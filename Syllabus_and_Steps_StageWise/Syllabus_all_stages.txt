First: don't recreate production exactly

Your Canam environment has things like GKE, Shared VPC, Cloud SQL, PgBouncer, RabbitMQ, JayDeBeApi/JDBC, GCS Fuse, Terraform, Helm, Snowpipe, DBT, Azure Pipelines, etc.

Trying to reproduce all of that immediately will teach you less because you'll spend most of your time fighting infrastructure.

Instead, build this in 8 stages.

Stage 3 — Build JDBC Source Connector

Now reproduce the important logic from:

JdbcSourceConnector

Your connector should do:

Build query
   ↓
Execute query
   ↓
fetchmany()
   ↓
Convert rows → dict
   ↓
Clean data
   ↓
Serialize JSON
   ↓
Return batch

For example:

class SQLServerSourceConnector(SourceConnector):

    def extract(self, context):

        if self.cursor is None:
            self.cursor = self.conn.cursor()

            query = self._build_query(context)

            self.cursor.execute(query)

        batch = self.cursor.fetchmany(self.limit)

        if not batch:
            return False

        records = [
            dict(zip(self.columns, row))
            for row in batch
        ]

        self.extracted_data = self._serialize(
            records,
            context
        )

        return True

Now you have essentially recreated the source half of the Canam ingestion framework.

Stage 4 — Build the ExtractionOperator

This is one of the most important parts of your project.

Your Canam operator is essentially implementing:

              ExtractionOperator
                      │
          ┌───────────┴───────────┐
          │                       │
      Producer                 Consumer
          │                       │
      Source                   Target
          │                       │
      extract()                save()
          │                       │
          ▼                       ▼
        Queue ────────────────► Target

The producer:

while source.extract(context):

    data = source.get_data()

    queue.put(data)

The consumer:

while True:

    data = queue.get()

    if data is None:
        break

    target.save(
        data=data,
        context=context
    )
Why your Canam implementation uses a queue

Because extraction and loading can overlap.

For example:

Time →

Source:
Batch 1 ── Batch 2 ── Batch 3 ── Batch 4
           ↓
Target:
       Batch 1 ── Batch 2 ── Batch 3

Instead of:

Extract 1
Load 1
Extract 2
Load 2
Extract 3
Load 3

you can pipeline them.

This is an important concept to understand deeply for interviews.

Stage 6 — Implement Full Load vs Delta Load

This is where your project becomes much more valuable.

Suppose your source table has:

CustomerID
PersonID
StoreID
TerritoryID
AccountNumber
ModifiedDate

Use:

ModifiedDate

as your delta column.

First execution

No XCom checkpoint exists.

Therefore:

XCom = NULL

        ↓

FULL LOAD

Example:

SELECT *
FROM Customer

After successful processing:

MAX(ModifiedDate)
        ↓
XCom

For example:

2026-08-24 14:30:00
Second execution

Airflow retrieves:

2026-08-24 14:30:00

Then query:

SELECT *
FROM Customer
WHERE ModifiedDate > '2026-08-24 14:30:00'

Now:

XCom exists
       ↓
STREAM / DELTA

This is exactly the concept your _determine_prefix() and _get_last_checkpoint() are supporting.

Stage 8 — Recreate the configuration-driven Snowpipe framework

    stage: sqlserver_stg
