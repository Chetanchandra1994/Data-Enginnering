# 1. MY PROJECT — 60-SECOND INTERVIEW INTRODUCTION

I built an end-to-end cloud-based data engineering pipeline using AdventureWorks as the source system.

The source data comes from SQL Server. I use Python for extraction and batching, and the extracted data is landed into object storage. Snowflake is used as the analytical platform, with separate layers for LANDING, PREPARE, NORMALIZE, SCHEMATIZE and MARKETPLACE.

I use dbt for transformations, data modeling and data quality testing. Terraform is used for infrastructure as code, and Azure DevOps is used for CI/CD. I implemented workload identity federation between Azure DevOps and Google Cloud instead of using service account JSON keys.

For environment management, I implemented separate DEV and TEST Terraform states in GCS and configured Azure DevOps environments with manual approval gates.

The current CI/CD flow is:

GitHub → Azure DevOps → Python validation → dbt validation → Terraform validation → Terraform plan → approval → Terraform apply → Snowflake.

The pipeline is designed to eventually support DEV → TEST → PRE-PROD → PROD promotion.

# 4. SQL INTERVIEW QUESTIONS

## Q1. What is the difference between WHERE and HAVING?

WHERE filters rows before aggregation.

HAVING filters groups after aggregation.

Example:

SELECT CustomerID, COUNT(*)
FROM Sales
WHERE OrderDate >= '2025-01-01'
GROUP BY CustomerID
HAVING COUNT(*) > 10;

Interview answer:

"WHERE filters individual rows before GROUP BY, while HAVING filters aggregated groups after GROUP BY."

---

## Q2. INNER JOIN vs LEFT JOIN?

INNER JOIN returns matching records from both tables.

LEFT JOIN returns all records from the left table and matching records from the right table.

In data engineering, LEFT JOIN is commonly useful for identifying missing reference data.

Example:

SELECT f.ProductKey
FROM FactSales f
LEFT JOIN DimProduct p
ON f.ProductKey = p.ProductKey
WHERE p.ProductKey IS NULL;

This is a referential integrity check.

---

## Q3. What is a window function?

A window function performs calculations across related rows without collapsing them into a single row.

Examples:

ROW_NUMBER()
RANK()
DENSE_RANK()
SUM() OVER()
LAG()
LEAD()

Example:

ROW_NUMBER() OVER (
PARTITION BY CustomerID
ORDER BY OrderDate DESC
)

This can be used to identify the latest record for each customer.

---

## Q4. ROW_NUMBER vs RANK vs DENSE_RANK?

ROW_NUMBER gives unique sequential numbers.

RANK gives the same rank to ties and leaves gaps.

DENSE_RANK gives the same rank to ties but does not leave gaps.

---

## Q5. How would you remove duplicates?

One common approach:

WITH ranked AS (
SELECT *,
ROW_NUMBER() OVER (
PARTITION BY BusinessKey
ORDER BY UpdatedAt DESC
) AS rn
FROM source_table
)
SELECT *
FROM ranked
WHERE rn = 1;

---

## Q6. What is a primary key?

A column or combination of columns that uniquely identifies a row.

---

## Q7. What is a surrogate key?

A system-generated key used instead of a business/natural key.

Example:

CustomerKey = 1001

instead of:

CustomerID = CUST123

Surrogate keys are especially useful in dimensional modeling.

## Q17. Why JSONL?

## Q18. Why did you use `default=str` with json.dumps?

Some SQL Server values such as Decimal and datetime are not directly JSON serializable.

Using:

json.dumps(record, default=str)

converts unsupported values to strings.

In production, however, I would carefully control the data types rather than blindly converting everything to strings.

# 8. DATA INGESTION QUESTIONS

## Q20. Full load vs incremental load?

Full load:

Extract everything every time.

Incremental:

Extract only newly added or changed records.

Full load is simpler but becomes expensive as data grows.

Incremental is more scalable.

---

## Q21. What is CDC?

Change Data Capture identifies inserts, updates and deletes from a source system.

A CDC pipeline can process only changed records instead of repeatedly extracting the entire source.

---

## Q22. How would you implement incremental extraction?

Possible strategies:

WHERE LastModifiedDate > last_successful_timestamp

or using:

* CDC
* SQL Server Change Tracking
* transaction logs
* source-specific CDC mechanisms

A robust pipeline stores the last successful watermark.

---

## Q23. What happens if a pipeline fails halfway?

I would design the pipeline to be restartable.

Important techniques:

* checkpoints/watermarks
* idempotency
* retries
* staging areas
* atomic writes
* audit tables
* dead-letter/error handling

# 16. WORKLOAD IDENTITY FEDERATION

## Q50. Why didn't you use a Google service account JSON key?

Because long-lived service account keys create security risks.

I implemented Workload Identity Federation.

Azure DevOps obtains an OIDC token and Google validates the token through the configured WIF provider.

Then the pipeline impersonates the Google service account.

---

## Q51. Explain your WIF flow.

Azure DevOps
↓
OIDC token
↓
Google Workload Identity Federation
↓
WIF provider validates token
↓
Google service account impersonation
↓
GCP resources

The pipeline does not store a long-lived Google service account private key.

---

## Q52. What is OIDC?

OpenID Connect is an identity layer built on OAuth 2.0.

In this case, Azure DevOps issues an identity token that Google trusts through WIF configuration.

---

## Q53. What is service account impersonation?

The external identity is authorized to act as a Google service account.

The pipeline receives temporary credentials rather than storing a permanent service account key.

## Q58. Why shouldn't secrets be committed to Git?

Because Git history can retain secrets even after a file is deleted.

In my project, a Terraform passphrase file was accidentally committed.

I removed it from Git history using history rewriting and force-pushed the cleaned repository.

## Q59. What should you do if a secret is accidentally committed?

Immediately:

1. Revoke/rotate the secret.
2. Remove it from the repository.
3. Remove it from Git history.
4. Check logs and downstream systems.
5. Update the secret securely.
6. Add `.gitignore` and secret scanning controls.

# 24. IDEMPOTENCY

## Q72. What is idempotency?

Running the same operation multiple times should not create incorrect duplicate results.

For example:

If a file is processed twice, the pipeline should not insert the same business records twice.

Techniques:

* unique keys
* MERGE
* processed-file tracking
* deterministic file names
* checkpoints
* transactional loading

## Q74. Pipeline failed after loading half the data. What do you do?

I would avoid blindly rerunning the entire pipeline.
