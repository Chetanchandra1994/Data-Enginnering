# SOP-01 — CLONING any Enterprise AIRFLOW ARCHITECTURE INTO THE PRACTICE PROJECT

**Project:** Data Engineering End-to-End Practice Project
**Purpose:** Reproduce the relevant any Enterprise Airflow/DAG deployment architecture in an isolated personal GCP + Azure DevOps environment.

---

# 1. Objective

The objective of this exercise was to take the Airflow/DAG deployment structure used at any Enterprise and reproduce its architecture in a personal practice environment without connecting the practice project to any Enterprise infrastructure.

The resulting practice architecture is:

```text
                         GIT REPOSITORY
                              |
                              v
                    Azure DevOps Pipeline
                              |
             +----------------+----------------+
             |                                 |
             v                                 v
        Unit Tests                         Deployment
             |                                 |
             v                                 v
        Docker Image                       TEST GCS
             |                                 |
             |                          Manual/automated
             |                           verification
             |                                 |
             +----------------+----------------+
                              |
                              v
                       PROD approval
                              |
                              v
                          PROD GCS
                              |
                              v
                       Airflow environment
```

The controlled deployment implementation additionally performs:

```text
Git commit
    |
    v
git diff HEAD~1 HEAD
    |
    +---- A -> copy
    +---- M -> copy
    +---- D -> delete
    +---- R -> delete old + copy new
```

Only changed DAG/plugin files are deployed.

# 14. Challenge — Docker Image Dependency Failure

One challenge encountered was that the Airflow container did not initially have every Python dependency required by the project tests.

Example:

```text
ModuleNotFoundError
```

The solution was:

1. Identify missing dependency.
2. Add dependency to `requirements.txt`.
3. Rebuild the Docker image.
4. Push the new image to Artifact Registry.
5. Pull/use the updated image.
6. Re-run tests.

This established an important production principle:

```text
requirements.txt
       ↓
Dockerfile
       ↓
Docker image
       ↓
Artifact Registry
       ↓
CI pipeline
```

Dependencies should be reproducible through the image rather than manually installed on individual machines.

```bash

```

then:

```bash
docker run --rm \
  -v $(Build.SourcesDirectory)/airflow-practice:/workspace \
  -w /workspace \
  -e PYTHONPATH=/workspace:/workspace/plugins \
  -e PYTEST_ADDOPTS="-p no:cacheprovider" \
```

Conceptually:

```text

    +

    ↓

```

The image supplies the runtime.

The mounted repository supplies the current code being tested.

# 25. Controlled Deployment

The original full-copy deployment created a serious problem:

```text
TEST contains:
A
B
C

Developer 1 changes A

Pipeline:
copy everything in TEST

PROD receives:
A
B
C
```

This could unintentionally promote another developer's work.

The solution was changed-file deployment.

---

# 26. Changed File Detection

[PIPELINE AGENT]

```bash
git diff --name-status -M HEAD~1 HEAD
```

Example:

```text
M airflow-practice/DAGS/foo.py
A airflow-practice/DAGS/new.py
D airflow-practice/DAGS/old.py
R100 airflow-practice/DAGS/a.py airflow-practice/DAGS/b.py
```

Meaning:

```text
A = Added
M = Modified
D = Deleted
R = Renamed
```

---

# 27. Rename Detection

The `-M` option enables rename detection:

```bash
git diff --name-status -M HEAD~1 HEAD
```

A rename may appear as:

```text
R095
```

rather than exactly:

```text
R100
```

Therefore the pipeline intentionally checks:

```bash
[[ "$status" == R* ]]
```

rather than:

```bash
[[ "$status" == "R100" ]]
```

This handles different Git rename similarity scores.

---

# 28. Rename Deployment Logic

GCS does not use the same native rename operation as a local filesystem.

Therefore:

```text
Rename:
old.py → new.py
```

becomes:

```text
DELETE old.py
COPY new.py
```

The deployment logic:

```bash
gcloud storage rm "gs://bucket/path/old.py"

gcloud storage cp \
  "local/path/new.py" \
  "gs://bucket/path/new.py"
```

---

# 29. Idempotent Deletion

A problem encountered was:

```text
gcloud storage rm
```

failing if the object was already absent.

The solution was to check existence first:

```bash
if gcloud storage ls \
  "gs://bucket/path/file.py" \
  >/dev/null 2>&1
then
    gcloud storage rm \
      "gs://bucket/path/file.py"
else
    echo "File is already absent"
fi
```

This makes deletion idempotent.

# 31. Multi-Developer Safety Test

Scenario:

```text
Developer A
    |
    +--> Change A
    |
    +--> TEST

Developer B
    |
    +--> Change B
    |
    +--> TEST
    |
    +--> PROD
```

Then A was deployed later.

Because the pipeline processes:

```bash
git diff HEAD~1 HEAD
```

A's deployment only contained A's changed files.

It did not perform:

```text
copy entire TEST bucket
```

Therefore B's newer files were not automatically copied by A's deployment.

This demonstrated the main controlled-deployment objective.

---

# 32. Important Limitation Discovered

The testing also exposed an important limitation.

Scenario:

```text
Developer A
    |
    v
older commit
    |
    v
TEST

Developer B
    |
    v
newer commit
    |
    v
TEST
    |
    v
PROD

Developer A
    |
    v
older commit
    |
    v
PROD
```

The changed-file mechanism prevents unrelated files from being copied, but it does not by itself prevent an older deployment from modifying a file after a newer deployment.

Therefore two separate problems must be distinguished:

```text
Problem 1:
Which files does THIS commit change?
        ↓
Solved by A/M/D/R detection.

Problem 2:
Can an older deployment overwrite newer PROD state?
        ↓
Not solved by the current mechanism.
```

This becomes a future advanced CI/CD improvement.

# 34. Three Deployment Controls

### `dependsOn`

```yaml
dependsOn: deploy_test
```

Means:

```text
deploy_prod depends on deploy_test
```

### `condition`

```yaml
condition: and(
  succeeded(),
  eq(variables['Build.SourceBranch'], 'refs/heads/main')
)
```

Means:

```text
previous dependency must succeed
AND
execution must be from main
```

### Azure Environment approval

```yaml
environment: 'PROD - Airflow DAGS'
```

means the PROD deployment is subject to the checks/approval configured on that Azure Environment.

The three concepts are:

```text
dependsOn
    =
dependency/order

condition
    =
eligibility

Environment approval
    =
authorization
```

The overall dependency order

The easiest way to remember the architecture is:

1. GCP Project
       ↓
2. APIs + Billing
       ↓
3. GCP Service Account + IAM
       ↓
4. Artifact Registry
       ↓
5. Custom Airflow Docker Image
       ↓
6. TEST GCS Bucket
       ↓
7. PROD GCS Bucket
       ↓
8. Azure DevOps Project/Repo
       ↓
9. Azure Secure File
       ↓
10. Azure Pipeline Variables
       ↓
11. Azure TEST Environment
       ↓
12. Azure PROD Environment + Approval
       ↓
13. Branch Policies + Build Validation
       ↓
14. Local Airflow Docker Compose
       ↓
15. DAGs + Plugins + Tests
       ↓
16. Feature Branch → PR → main
       ↓
17. Unit Tests
       ↓
18. TEST GCS Deployment
       ↓
19. PROD Approval
       ↓
20. PROD GCS Deployment

The minimum cloud/DevOps resource set for your current controlled-deployment pipeline is therefore essentially:

GCP Project → Service Account/IAM → Artifact Registry → Airflow image → 2 GCS buckets → Azure Repo → Secure File → Pipeline → 2 Azure Environments → PROD approval → Branch/PR policies
