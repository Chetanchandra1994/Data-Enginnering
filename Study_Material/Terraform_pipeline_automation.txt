Step 2.2 — Use this initial CI pipeline

trigger:
  branches:
    include:
      - main

pr:
  branches:
    include:
      - main

pool:
  vmImage: ubuntu-latest

stages:

# ============================================================
# 1. TERRAFORM CI VALIDATION
# ============================================================

- stage: TerraformValidation
  displayName: 'Terraform CI Validation'

  jobs:
    - job: ValidateTerraform
      displayName: 'Validate Terraform'

      steps:

        # ----------------------------------------------------
        # Checkout
        # ----------------------------------------------------

        - checkout: self

        # ----------------------------------------------------
        # Install Terraform
        # ----------------------------------------------------

        - script: |
              curl -fsSL https://releases.hashicorp.com/terraform/1.15.8/terraform_1.15.8_linux_amd64.zip -o /tmp/terraform.zip
              rm -rf /tmp/terraform-install
              mkdir -p /tmp/terraform-install
              unzip -o /tmp/terraform.zip -d /tmp/terraform-install
              chmod +x /tmp/terraform-install/terraform
              /tmp/terraform-install/terraform version
              echo "##vso[task.prependpath]/tmp/terraform-install"
          displayName: 'Install Terraform'

        # ----------------------------------------------------
        # Terraform Format Check
        # ----------------------------------------------------

        - script: |
            cd terraform

            terraform fmt -check -recursive

          displayName: 'Terraform Format Check'

        # ----------------------------------------------------
        # Terraform Init
        # ----------------------------------------------------

        - script: |
            cd terraform

            terraform init -backend=false

          displayName: 'Terraform Init'

        # ----------------------------------------------------
        # Terraform Validate
        # ----------------------------------------------------

        - script: |
            cd terraform

            terraform validate

          displayName: 'Terraform Validate'

Step 2.3 — Why terraform init -backend=false here?

This is an important CI/CD distinction.

For validation, we don't need to connect to the real remote state.

CI validation
     │
     ├── fmt
     ├── init -backend=false
     └── validate

Therefore:

terraform init -backend=false

prevents the validation job from interacting with your GCS state.

This makes the PR validation safer.

Later, when we perform an actual plan/apply, we will initialize the appropriate remote state:

terraform init \
  -reconfigure \
  -backend-config="prefix=terraform/state/test"

Your existing TEST pipeline design already uses this pattern.

Step 7 — Do NOT put secrets in azure-pipelines.yml

Never do this:

snowflake_password: "mypassword"

or:

snowflake_private_key: |
  -----BEGIN PRIVATE KEY-----

or:

SNOWFLAKE_PRIVATE_KEY_PASSPHRASE: "password123"

Instead:

Azure DevOps
    │
    ├── Secure Files
    │       └── snowflake_tf_key.p8
    │
    ├── Variable Groups / Secret Variables
    │       └── SNOWFLAKE_PRIVATE_KEY_PASSPHRASE
    │
    └── Service Connection
            └── google-cloud-wif

Our earlier pipeline already follows this approach by downloading snowflake_tf_key.p8 through DownloadSecureFile@1 and supplying the passphrase through TF_VAR_snowflake_private_key_passphrase.

Step 8 — GCP authentication architecture

For the actual Terraform plan/apply jobs, we'll use:

Azure DevOps
      │
      │ Azure Service Connection
      ▼
Azure CLI
      │
      │ Federated ID token
      ▼
Google STS
      │
      ▼
Workload Identity Federation
      │
      ▼
terraform-ci@
      │
      ├── GCS
      ├── Pub/Sub
      └── other required GCP resources

No GCP service-account JSON key is required.

Your saved implementation already creates the external-account configuration and uses:

gcloud auth login \
  --cred-file="$GOOGLE_APPLICATION_CREDENTIALS"

with the Azure DevOps federated token.

This is a much better enterprise pattern than putting a long-lived GCP JSON key into Azure DevOps.

Step 9 — Important correction to our deployment design

There is one thing I want us to improve before we automate DEV → TEST → PREPROD → PROD.

Earlier we had:

Plan TEST
   ↓
Apply TEST

but the best enterprise implementation is:

Terraform Plan
      ↓
SAVE PLAN FILE
      ↓
Publish Artifact
      ↓
Approval
      ↓
Apply EXACT SAME PLAN

For example:

terraform plan \
  -var-file=environments/test.tfvars \
  -out="$(Build.ArtifactStagingDirectory)/test.tfplan"

Then:

test.tfplan
     ↓
Pipeline Artifact
     ↓
TEST deployment
     ↓
terraform apply test.tfplan

Your earlier saved pipeline design already contains this concept: it creates test.tfplan and publishes it as the terraform-plan-test artifact.

We should use this approach rather than running a fresh plan during apply.

Why?

Because:

Plan at 10:00
       ↓
Infrastructure changes
       ↓
Apply at 10:30

could produce a different plan if we run terraform plan again.

Using the saved plan gives:

REVIEWED PLAN
     ↓
EXACT PLAN
     ↓
APPLIED PLAN

That's a very important senior-level CI/CD concept.
