Your architecture is:

There are two completely separate authentication paths.

Let's understand the GCP side first.

1. What is OIDC?

OIDC = OpenID Connect.

At a simple level:

OIDC is a standard way for one system to prove the identity of a user/workload to another system.

In your case:

Azure DevOps
      ↓
"I am an authorized Azure DevOps pipeline."
      ↓
OIDC token

Azure DevOps can issue a short-lived identity token for the pipeline.

That token contains claims describing the workload, such as information about the issuer, organization/project/repository/pipeline context, etc.

Think of it as a temporary digital ID card.

2. What is JWT?

JWT = JSON Web Token.

OIDC tokens are commonly represented as JWTs.

A JWT conceptually looks like:

HEADER.PAYLOAD.SIGNATURE

The payload contains claims.

For example, conceptually:

{
  "iss": "https://vstoken.dev.azure.com/...",
  "sub": "...",
  "aud": "...",
  "iat": "...",
  "exp": "..."
}

You don't need to memorize the exact claims yet.

The important thing is:

Azure DevOps creates a signed, short-lived token that represents the pipeline's identity.

Old approach

You would have something like:

That credential could potentially remain valid for a long time.

There is no permanent GCP service-account private key stored in Azure DevOps.

That's the key advantage.

4. What exactly is Workload Identity Federation?

This is the part people often confuse.

Workload Identity Federation (WIF) is essentially Google's mechanism for saying:

"I trust identities coming from this external identity provider, and under specific conditions I will allow them to act as this GCP service account."

In your case:

Azure DevOps
     │
     │ OIDC token
     ▼
Google Workload Identity Provider
     │
     │ validate token + claims
     ▼
Workload Identity Pool
     │
     │ authorized?
     ▼
terraform-ci Service Account
     │
     ▼
GCP resources

So WIF is the bridge between:

Azure DevOps identity

and:

GCP service-account identity
5. What is the Workload Identity Pool?

Think of the pool as a logical container for external identities.

Conceptually:

GCP
│
└── Workload Identity Pool
       │
       └── Azure DevOps Provider
              │
              └── Azure DevOps pipeline identity

The pool doesn't itself give unlimited access.

It provides the identity federation framework.

6. What is the Workload Identity Provider?

The provider tells Google:

"This external identity comes from Azure DevOps, and here is how you should validate it."

Conceptually:

Workload Identity Pool
          │
          └── Provider
                │
                └── Azure DevOps OIDC

The provider knows the OIDC issuer and configuration required to validate the token.

7. Then how does terraform-ci become involved?

This is the most important part.

You have:

Azure DevOps
      ↓
OIDC token
      ↓
WIF Provider
      ↓
terraform-ci Service Account

There must be a permission relationship saying:

This federated Azure DevOps workload is allowed to impersonate/use terraform-ci.

So the final identity that Terraform operates as is:

terraform-ci@electric-tesla-507710-k2.iam.gserviceaccount.com

That's why we call terraform-ci the machine identity for your Terraform deployment.

9. What is the difference between OIDC and WIF?

This is a great interview question.

OIDC

Provides the identity token.

OIDC
 ↓
"Here is who I am."
WIF

Provides the trust/federation mechanism that allows Google to accept that external identity.

WIF
 ↓
"I trust this external identity under these conditions."

So:

OIDC provides the identity assertion; Workload Identity Federation allows GCP to trust and exchange that external identity for access to GCP resources.

10. Where does terraform-ci fit?

terraform-ci is not OIDC.

It is not WIF.

It is a normal GCP service account:

terraform-ci@electric-tesla-507710-k2.iam.gserviceaccount.com

WIF allows your external Azure DevOps workload to obtain/use this identity without storing a permanent service-account key.

12. Why did our IAM command show nothing?

This now becomes an important distinction.

We checked:

Project-level IAM

and got nothing.

But WIF can involve permissions granted specifically to the federated identity/service account relationship, while Terraform's actual resource access can also be granted at resource level.

For example:

terraform-ci
     │
     ├── GCS state bucket → access
     │
     ├── GCS application bucket → access
     │
     ├── Pub/Sub → access
     │
     └── other resources → access

So don't conclude that WIF is broken just because the project IAM query returned nothing.

Your pipeline already successfully authenticates through WIF, so we know the federation path is functioning.

14. Question:
How does your Azure DevOps pipeline authenticate to GCP without storing service-account credentials?

Answer:
We use Workload Identity Federation with Azure DevOps OIDC. Azure DevOps obtains a short-lived OIDC token representing the pipeline workload. 
GCP validates that token through the configured Workload Identity Provider and allows the authorized workload to impersonate our Terraform CI service account. 
Terraform then accesses GCP using that service-account identity. This avoids storing a long-lived GCP service-account JSON key in Azure DevOps.
