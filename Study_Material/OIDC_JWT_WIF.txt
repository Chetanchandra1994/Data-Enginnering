# Understand Your WIF Architecture Properly

## Interview Question

**How does your Azure DevOps pipeline authenticate to GCP?**

### Strong Interview Answer

Our Azure DevOps pipeline uses **OIDC-based Workload Identity Federation** rather than storing a long-lived GCP service-account JSON key.

The pipeline obtains a **short-lived OIDC identity token**, represented as a JWT. GCP's configured **Workload Identity Provider** validates the token's issuer, audience and other configured claims and maps the external workload identity into our Workload Identity Pool.

The authorized federated identity has `roles/iam.workloadIdentityUser` on our `terraform-ci` service account, allowing the pipeline workload to use that service-account identity.

Terraform then accesses GCP using the permissions granted to `terraform-ci`.

This avoids storing a long-lived GCP service-account private key in Azure DevOps.

# 3. What Is OIDC?

**OIDC = OpenID Connect.**

OIDC is an identity protocol built on OAuth 2.0.

Its purpose here is essentially:

> "Here is a signed assertion describing the identity of this workload."

In your architecture, the Azure DevOps workload obtains an identity token that can be presented to GCP.

Think of OIDC as the **identity language/protocol** used to communicate:

```text
"I am this particular workload."
```

The token contains claims that allow the receiving system to determine things such as:

* who issued the token
* who/what the subject is
* who the token is intended for
* when it was issued
* when it expires
* other identity/context claims

---

# 4. What Is a JWT?

**JWT = JSON Web Token.**

JWT is a **token format**.

An OIDC ID token is commonly encoded as a JWT.

Conceptually:

```text
HEADER.PAYLOAD.SIGNATURE
```

The payload contains claims such as:

```json
{
  "iss": "...",
  "sub": "...",
  "aud": "...",
  "iat": "...",
  "exp": "..."
}
```

You do not need to memorize the exact claim structure.

The important distinction is:

```text
OIDC = protocol
JWT  = token format
```

So do **not** think:

```text
OIDC → JWT → WIF
```

as three independent authentication systems.

A better mental model is:

```text
OIDC
 │
 │ uses an ID token
 ▼
JWT-formatted token
 │
 ▼
GCP WIF
```

---

# 5. What Is the OIDC Token Doing?

The token is essentially a **temporary, signed identity assertion**.

It says something conceptually like:

```text
"I represent this authorized external workload."
```

It is:

* signed
* short-lived
* associated with an issuer
* associated with an audience
* associated with a subject
* subject to validation

The token itself does **not** mean:

> "Give me Administrator access to GCP."

It only establishes an identity that GCP can evaluate.

Permissions come later through IAM.

# 6. Why Not Store a GCP Service-Account JSON Key?

### Older approach

```text
Azure DevOps
      │
      │ service-account JSON key
      ▼
terraform-ci
      │
      ▼
GCP
```

A service-account JSON key contains a private cryptographic credential.

If stored in Azure DevOps:

```text
terraform-ci-key.json
```

that long-lived credential becomes something that must be protected, rotated and eventually revoked.

---

# 7. WIF Approach

Your architecture instead uses:

```text
Azure DevOps
      │
      │ short-lived identity token
      ▼
GCP WIF
      │
      ▼
terraform-ci
      │
      ▼
GCP
```

There is no long-lived **GCP service-account JSON private key** stored in Azure DevOps for this authentication path.

### Main advantage

You eliminate the need to distribute and permanently store a GCP service-account private key for the CI/CD workload.

This reduces:

* credential leakage risk
* secret-management burden
* key rotation requirements
* long-lived credential exposure

# 8. What Exactly Is Workload Identity Federation?

**WIF = Workload Identity Federation.**

WIF is Google's mechanism for allowing an **external workload identity** to access GCP without requiring a long-lived GCP service-account key.

Think of WIF as the **trust bridge**:

```text
External identity
       │
       │ "This is who I am."
       ▼
      WIF
       │
       │ "I trust this identity under these conditions."
       ▼
GCP service-account identity
```

In your case:

```text
Azure DevOps workload
        │
        ▼
   OIDC token
        │
        ▼
GCP WIF Provider
        │
        ▼
Federated identity
        │
        ▼
terraform-ci
```

---

# 9. What Is the Workload Identity Pool?

A **Workload Identity Pool** is a logical container for external identities.

Your pool is:

```text
azure-devops-pool
```

Conceptually:

```text
GCP
 │
 └── Workload Identity Pool
          │
          └── azure-devops-provider
                    │
                    └── External workload identity
```

The pool provides the federation boundary.

### Important

The pool does **not** mean:

```text
Pool = unlimited GCP access
```

It does not automatically grant permissions to GCP resources.

Actual access still depends on:

* which external identities are trusted
* which service accounts they can use
* which IAM roles those service accounts have

---

# 10. What Is the Workload Identity Provider?

The **Workload Identity Provider** tells GCP how to trust and validate an external identity source.

Your provider is:

```text
azure-devops-provider
```

It belongs to:

```text
azure-devops-pool
```

The provider contains configuration such as:

```text
OIDC issuer
Allowed audience
Attribute mapping
```

Conceptually:

```text
Workload Identity Pool
          │
          └── Provider
                │
                ├── Who issued the token?
                ├── What audience is allowed?
                ├── How are claims mapped?
                └── Which external identity does this represent?
```

---

# 11. What Does the Provider Actually Do?

When the external token reaches GCP, the provider configuration allows GCP to validate the identity assertion.

Conceptually, GCP checks:

```text
Is the token from the trusted issuer?
          │
          ▼
Is the audience correct?
          │
          ▼
Is the token valid/not expired?
          │
          ▼
Do the relevant claims satisfy the federation configuration?
          │
          ▼
What federated identity does this represent?
```

Only after this identity is established does the IAM authorization relationship become relevant.

---

# 12. What Is the Federated Identity?

The external Azure DevOps workload is represented inside GCP as a **federated principal**.

Your actual configuration contains a subject-based principal similar to:

```text
principal://iam.googleapis.com/projects/
776178390591/locations/global/
workloadIdentityPools/azure-devops-pool/
subject/...
```

This is important because GCP does not simply say:

> "Anything coming from Azure DevOps can use terraform-ci."

Instead, a specific federated identity is authorized.

# 13. Where Does `terraform-ci` Come In?

This is one of the most important concepts.

Your service account is:

```text
terraform-ci@electric-tesla-507710-k2.iam.gserviceaccount.com
```

It is a **normal GCP service account**.

It is not:

* OIDC
* JWT
* WIF
* the Workload Identity Pool
* the Workload Identity Provider

Instead:

```text
terraform-ci
```

is the **GCP machine identity** that Terraform ultimately operates as.

---

# 14. What Does `roles/iam.workloadIdentityUser` Do?

Your service account has an IAM binding allowing the federated identity to use it.

Conceptually:

```text
Federated Azure DevOps identity
             │
             │ roles/iam.workloadIdentityUser
             ▼
      terraform-ci
```

This permission means, approximately:

> "This authorized federated identity is allowed to use/impersonate this service account."

It does **not** mean:

> "This service account can do everything in GCP."

Those are two different permission questions.

---

# 15. The Two IAM Questions

This is extremely important for interviews.

### Question 1

**Can this external workload use the service account?**

Controlled by the federation/service-account relationship:

```text
roles/iam.workloadIdentityUser
```

### Question 2

**What can the service account actually do?**

Controlled by IAM roles granted to:

```text
terraform-ci
```

on GCP resources.

For example:

```text
terraform-ci
     │
     ├── Terraform state bucket → permissions
     │
     ├── GCS resources → permissions
     │
     ├── Pub/Sub → permissions
     │
     └── other GCP resources → permissions
```

Therefore:

```text
WIF authorization
        ≠
Resource authorization
```

Both are required.

# 19. OIDC vs WIF — Interview Question

### Question

**What is the difference between OIDC and Workload Identity Federation?**

### Answer

OIDC is an identity protocol used to provide a verifiable identity assertion.

Workload Identity Federation is Google's mechanism for establishing trust with that external identity and allowing it to access GCP without requiring a long-lived service-account key.

In simple terms:

```text
OIDC
 ↓
"I am this workload."

WIF
 ↓
"GCP trusts this external identity under these configured conditions."
```

Then:

```text
Federated identity
       ↓
terraform-ci
       ↓
IAM permissions
       ↓
GCP
```

# 20. Is JWT the Authentication System?

No.

This is a common interview trap.

JWT is a **token format**.

OIDC is the **identity protocol**.

WIF is the **GCP federation mechanism**.

Therefore:

```text
JWT ≠ OIDC
JWT ≠ WIF
JWT ≠ IAM
JWT ≠ Service Account
```

A JWT is simply one way identity information is represented in the token.

---

# 21. Does WIF Give Permissions?

No.

This is another important distinction.

WIF establishes/trusts the external identity relationship.

The service account's IAM permissions determine what it can actually do.

Therefore:

```text
WIF
  ↓
Identity established
  ↓
Service account
  ↓
IAM roles
  ↓
Resource access
```

Think:

> **Authentication/federation answers "Who are you?"**

> **Authorization/IAM answers "What are you allowed to do?"**

# 24. Why Did Our Project-Level IAM Query Return Nothing?

This is an important lesson.

We checked project-level IAM for:

```text

```

and did not find a matching project-level binding.

That does **not** mean:

```text

```

because IAM can be granted at different resource levels.

For example:

```text
Organization
    ↓
Folder
    ↓
Project
    ↓
Bucket / Pub/Sub / other resource
```

A service account may have permissions directly on a specific resource without having a project-level role.

Therefore:

```text
No project-level binding
        ≠
No GCP access
```

# 28. Your One-Minute Interview Explanation

If an interviewer asks:

**"Explain how your Azure DevOps pipeline authenticates to GCP."**

Say:

> Our Azure DevOps pipeline uses OIDC-based Workload Identity Federation instead of storing a long-lived GCP service-account JSON key.
>
> The pipeline obtains a short-lived OIDC identity token, which is represented as a JWT. GCP validates that token through the configured Workload Identity Provider, including the issuer, audience and relevant identity claims.
>
> The external workload is represented as a federated identity in our `azure-devops-pool`. That federated identity is authorized with `roles/iam.workloadIdentityUser` to use our `terraform-ci` service account.
>
> Terraform then operates using the `terraform-ci` service-account identity, and its actual access to GCP resources is determined by the IAM roles granted to that service account.
>
> This allows us to authenticate Azure DevOps to GCP without storing a long-lived GCP service-account private key.
