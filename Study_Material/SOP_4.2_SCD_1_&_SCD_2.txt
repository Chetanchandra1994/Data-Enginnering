# CDC, Incremental Loading, SCD Type 1 & SCD Type 2

## AdventureWorks Data Engineering Practice Project

---

# 1. Objective

Implement and understand an end-to-end change-data pipeline:

```text
SQL Server Source
      │
      │ New / Changed Data
      ▼
CDC / Incremental Detection
      │
      ▼
Python Extraction
      │
      ▼
GCS
      │
      ▼
Pub/Sub Notification
      │
      ▼
Snowpipe
      │
      ▼
Snowflake LANDING
      │
      ├───────────────┐
      ▼               ▼
     SCD1            SCD2
      │               │
      ▼               ▼
Current State       Historical State
```

The important distinction is:

```text
CDC = How do I identify changes?

SCD1 = How do I store changes when I only want the latest value?

SCD2 = How do I store changes when I need historical versions?
```

---

# 2. CDC vs Incremental Loading vs SCD

These three concepts are related but are NOT the same thing.

| Concept          | Purpose                                                             |
| ---------------- | ------------------------------------------------------------------- |
| CDC              | Detect inserts/updates/deletes                                      |
| Incremental Load | Extract only data that changed/newly arrived since the previous run |
| SCD Type 1       | Store only the latest version                                       |
| SCD Type 2       | Preserve historical versions                                        |

Example:

Customer 29487 initially:

```text
Email = old@example.com
Income = 80000
```

Later:

```text
Email = new@example.com
Income = 90000
```

CDC asks:

```text
Did customer 29487 change?
```

SCD1 says:

```text
Keep only new@example.com / 90000
```

SCD2 says:

```text
Keep both versions and mark which one is current
```

# 4. Important CDC Limitation in Our Source

Our AdventureWorks `DimCustomer` table does NOT have a reliable:

```text
ModifiedDate
UpdatedAt
CreatedAt
LastModifiedTimestamp
```

Therefore:

```text
CustomerKey > previous_watermark
```

can detect:

```text
NEW RECORDS
```

but cannot detect:

```text
UPDATES TO EXISTING RECORDS
```

Example:

```text
CustomerKey = 29487
Email = old@example.com
```

Later:

```text
CustomerKey = 29487
Email = new@example.com
```

CustomerKey remains:

```text
29487
```

Therefore:

```sql
WHERE CustomerKey > 29487
```

will NOT detect the update.

This is one of the most important interview points.

# 5. CDC Strategies

In a production system, CDC can be implemented using several mechanisms.

## Option 1 — High-Watermark

Example:

```sql
WHERE CustomerKey > :last_watermark
```

Good for:

```text
new records
```

Not sufficient for:

```text
updates
deletes
```

---

## Option 2 — Modified Timestamp

If source has:

```text
ModifiedDate
```

then:

```sql
WHERE ModifiedDate > :last_watermark
```

can detect both:

```text
INSERT
UPDATE
```

assuming the timestamp is reliable.

---

## Option 3 — SQL Server Change Tracking

SQL Server can maintain changed primary keys.

Conceptually:

```text
Source Table
     │
     ▼
Change Tracking
     │
     ▼
Changed CustomerKeys
     │
     ▼
Read current records
```

---

## Option 4 — SQL Server CDC

SQL Server CDC captures row-level changes including operation information.

Conceptually:

```text
INSERT
UPDATE
DELETE
```

are captured separately.

---

## Option 5 — Database Log / Enterprise CDC

Production platforms may use tools such as:

```text
Debezium
Kafka
Oracle GoldenGate
Qlik Replicate
Fivetran
AWS DMS
Azure Data Factory CDC
```

depending on the environment.

# 12. Step 6 — Python Reads the Watermark

Python function:

```python
def get_watermark(cursor, pipeline_name):
    query = """
        SELECT WATERMARK_VALUE
        FROM dbo.ETL_Watermark
        WHERE PIPELINE_NAME = ?
    """

    cursor.execute(query, pipeline_name)

    row = cursor.fetchone()

    if row:
        return int(row[0])

    return 0
```

The pipeline therefore starts from:

```text
29483
```

# 13. Step 7 — Extract Only New Records

Core incremental query:

```sql
SELECT TOP (?)
    *
FROM dbo.DimCustomer
WHERE CustomerKey > ?
ORDER BY CustomerKey;
```

Python implementation:

```python
def extract_incremental_batch(
    cursor,
    table_name,
    watermark_column,
    watermark_value,
    batch_size
):
    query = f"""
        SELECT TOP (?)
            *
        FROM dbo.{table_name}
        WHERE [{watermark_column}] > ?
        ORDER BY [{watermark_column}]
    """

    cursor.execute(
        query,
        batch_size,
        watermark_value
    )

    columns = [column[0] for column in cursor.description]

    rows = cursor.fetchall()

    records = [
        dict(zip(columns, row))
        for row in rows
    ]

    return records
```

# 18. Production Improvement — Watermark Commit Point

Important:

Our current practice implementation updates the watermark after the GCS upload.

A production implementation should preferably treat the watermark as committed only after the downstream processing is confirmed successful:

```text
SQL Server
   │
   ▼
Extract
   │
   ▼
GCS
   │
   ▼
Pub/Sub
   │
   ▼
Snowpipe
   │
   ▼
Snowflake validation
   │
   ▼
SUCCESS
   │
   ▼
Update watermark
```

Why?

Suppose:

```text
Source extraction = SUCCESS
GCS upload        = SUCCESS
Snowpipe           = FAILED
Watermark          = already updated
```

Then the next run might skip those records.

Therefore, production systems normally coordinate:

```text
source checkpoint
+
pipeline audit
+
downstream success
```

before advancing the checkpoint.

# 26. Why LANDING Uses VARIANT

Our LANDING table contains:

```text
RAW_DATA       VARIANT
SOURCE_FILE    TEXT
LOAD_TIMESTAMP TIMESTAMP_NTZ
```

Example:

```json
{
  "CustomerKey": 29487,
  "FirstName": "Incremental",
  "EmailAddress": "incremental.test004@example.com",
  "YearlyIncome": 80000
}
```

stored as:

```text

```

Why?

Because LANDING should preserve the source payload with minimal transformation.

Benefits:

```text
Flexible schema
Raw data preservation
Easy schema evolution
Replay capability
Source auditing
Less coupling between ingestion and transformation
```

The business structure is created later through:

```text
PREPARE
NORMALIZE
SCHEMATIZE
MARKETPLACE
```

# 27. SCD Type 1

## Definition

SCD Type 1 means:

```text
Overwrite the old value with the new value.
```

There is no historical version retained in the target dimension.

Example:

Before:

```text
CustomerKey = 29487
Email = incremental.test004@example.com
Income = 80000
```

After:

```text
CustomerKey = 29487
Email = incremental.updated004@example.com
Income = 90000
```

Target contains only:

```text
29487 | incremental.updated004@example.com | 90000
```

# 29. Step 20 — Initial SCD1 MERGE

The important pattern is:

```sql
MERGE INTO TARGET
USING SOURCE
ON TARGET.CUSTOMER_KEY = SOURCE.CUSTOMER_KEY
```

Because LANDING may contain multiple versions of the same customer, we first select the latest version.

```sql
MERGE INTO ADVWORKS_DEV.NORMALIZE.DIM_CUSTOMER_INCREMENTAL AS TARGET

USING
(
    SELECT
        RAW_DATA:CustomerKey::INT AS CUSTOMER_KEY,
        RAW_DATA:CustomerAlternateKey::STRING AS CUSTOMER_ALTERNATE_KEY,
        RAW_DATA:GeographyKey::INT AS GEOGRAPHY_KEY,
        RAW_DATA:FirstName::STRING AS FIRST_NAME,
        RAW_DATA:LastName::STRING AS LAST_NAME,
        RAW_DATA:EmailAddress::STRING AS EMAIL_ADDRESS,
        RAW_DATA:YearlyIncome::NUMBER(18,2) AS YEARLY_INCOME,
        LOAD_TIMESTAMP
    FROM ADVWORKS_DEV.LANDING.DIM_CUSTOMER
    QUALIFY ROW_NUMBER() OVER
    (
        PARTITION BY RAW_DATA:CustomerKey
        ORDER BY LOAD_TIMESTAMP DESC
    ) = 1
) AS SOURCE

ON TARGET.CUSTOMER_KEY = SOURCE.CUSTOMER_KEY

WHEN MATCHED THEN UPDATE SET
    TARGET.EMAIL_ADDRESS = SOURCE.EMAIL_ADDRESS,
    TARGET.YEARLY_INCOME = SOURCE.YEARLY_INCOME,
    TARGET.UPDATED_TIMESTAMP = CURRENT_TIMESTAMP()

WHEN NOT MATCHED THEN INSERT
(
    CUSTOMER_KEY,
    CUSTOMER_ALTERNATE_KEY,
    GEOGRAPHY_KEY,
    FIRST_NAME,
    LAST_NAME,
    EMAIL_ADDRESS,
    YEARLY_INCOME,
    CREATED_TIMESTAMP,
    UPDATED_TIMESTAMP
)
VALUES
(
    SOURCE.CUSTOMER_KEY,
    SOURCE.CUSTOMER_ALTERNATE_KEY,
    SOURCE.GEOGRAPHY_KEY,
    SOURCE.FIRST_NAME,
    SOURCE.LAST_NAME,
    SOURCE.EMAIL_ADDRESS,
    SOURCE.YEARLY_INCOME,
    CURRENT_TIMESTAMP(),
    CURRENT_TIMESTAMP()
);
```

---

# 30. Why ROW_NUMBER Is Important

LANDING may contain:

```text
29487 | old email | old income | file 1
29487 | new email | new income | file 2
```

If we directly MERGE both records, we can get:

```text
multiple source rows match target
```

or nondeterministic behavior.

Therefore:

```sql
QUALIFY ROW_NUMBER() OVER
(
    PARTITION BY CUSTOMER_KEY
    ORDER BY LOAD_TIMESTAMP DESC
) = 1
```

means:

```text
For every customer,
choose the latest event.
```

This is a very useful production/interview pattern.

# 38. SCD Type 2

## Definition

SCD Type 2 preserves historical versions.

Instead of:

```text
OLD → overwritten
```

we do:

```text
OLD → expired

NEW → current
```

Example:

```text
29487 | old@example.com | 80000 | FALSE
29487 | new@example.com | 90000 | TRUE
```

```text

```

# 48. SCD1 vs SCD2

| Requirement         | SCD1                    | SCD2                |
| ------------------- | ----------------------- | ------------------- |
| Latest value        | Yes                     | Yes                 |
| Historical value    | No                      | Yes                 |
| Old row overwritten | Yes                     | No                  |
| Multiple versions   | No                      | Yes                 |
| `VALID_FROM`        | Usually No              | Yes                 |
| `VALID_TO`          | Usually No              | Yes                 |
| `IS_CURRENT`        | Usually No              | Yes                 |
| Storage             | Lower                   | Higher              |
| Query complexity    | Lower                   | Higher              |
| Typical use         | Current-state reporting | Historical analysis |

```text
regulatory/audit requirements
point-in-time analysis
historical dashboards
```

# 53. Interview Answer — "What is CDC?"

A strong answer:

> CDC, or Change Data Capture, is the mechanism used to identify inserts, updates and deletes from a source system so that only changed data is processed instead of repeatedly performing a full load. Depending on the source, I can use a high-watermark column, modification timestamp, SQL Server Change Tracking/CDC, database logs, or a dedicated CDC platform. In my AdventureWorks practice pipeline, I used CustomerKey as a high-watermark to demonstrate incremental inserts, but I explicitly treat that as insufficient for updates because CustomerKey does not change when an existing customer is modified.

---

# 54. Interview Answer — "How does your pipeline detect updates?"

Do NOT say:

> We use CustomerKey to detect updates.

That would be incorrect.

Say:

> CustomerKey watermarking handles newly inserted records because the key increases, but it does not detect updates to existing records. For production I would use a reliable change indicator such as ModifiedDate, SQL Server Change Tracking/CDC, or database-log-based CDC. Once the changed event reaches Snowflake, I use the business key to apply the appropriate SCD strategy.

---

# 55. Interview Answer — "What is SCD Type 1?"

> SCD Type 1 overwrites the existing dimension value with the latest value. It is appropriate when historical changes are not required and the business only needs the current state. In my implementation I use a MERGE keyed by CustomerKey, updating matched records and inserting new records.

---

# 56. Interview Answer — "What is SCD Type 2?"

> SCD Type 2 preserves historical versions of dimension records. When a change arrives, I expire the current version by setting VALID_TO and IS_CURRENT to false, then insert the new version with a new VALID_FROM, NULL VALID_TO and IS_CURRENT=true. This allows point-in-time and historical analysis.

---

# 57. Interview Answer — "Can CDC and SCD be used together?"

Yes.

They solve different problems:

```text
CDC
↓
Find what changed

SCD
↓
Decide how the changed dimension should be stored
```

For example:

```text
CDC detects:
Customer 29487 changed

SCD1:
Overwrite current customer

SCD2:
Expire old version + create new version
```

---

# 58. Golden Rules to Remember

```text
1. CDC ≠ SCD.

2. CDC detects changes.

3. Incremental loading reduces the amount of data extracted.

4. A high-watermark can detect inserts only if the watermark column is monotonically increasing.

5. A primary key is NOT automatically a CDC column.

6. Updates require a reliable change indicator.

7. SCD1 keeps the latest value.

8. SCD2 keeps history.

9. LANDING should preserve raw events.

10. Deduplicate before MERGE when multiple versions can exist.

11. Snowpipe handles file ingestion, not business-level SCD logic.

12. dbt should handle downstream transformations/modeling.

13. The watermark should ideally advance only after successful downstream processing.

14. Idempotency is required so retries do not create duplicate business data.
```
