Step 2 — Configure Terraform backend and provider

versions.tf:

terraform {
  required_version = ">= 1.5.0"

  backend "gcs" {
    bucket = "electric-tesla-507710-k2-tfstate"
    prefix = "terraform/state/dev"
  }

  required_providers {
    snowflake = {
      source  = "snowflakedb/snowflake"
      version = "~> 2.0"
    }
  }
}
Why?

Terraform state is stored remotely in GCS instead of only on your laptop.

Terraform
    ↓
GCS remote state

This is important for CI/CD and team environments.

Step 3 — Configure Snowflake authentication through variables

variables.tf contains:

  type = string
}

}

  type = string
}

  type      = string
  sensitive = true
}

variable "snowflake_role" {
  type    = string
  default = "ACCOUNTADMIN"
}

variable "snowflake_warehouse" {
  type = string
}

variable "snowflake_database" {
  type = string
}

variable "environment" {
  type = string
}
Important security principle

We do not commit:

private key
passphrase
credentials

The private key remains locally under:

$HOME\.snowflake\snowflake_tf_key.p8

and secrets are supplied through environment variables/CI secrets.

Step 13 — Use Terraform yamldecode() to read metadata

locals.tf reads the YAML:

locals {
  tables_config = yamldecode(
    file("${path.module}/config/tables.yml")
  )

  stages_config = yamldecode(
    file("${path.module}/config/stages.yml")
  )

  file_formats_config = yamldecode(
    file("${path.module}/config/file-formats.yml")
  )

  pipes_config = yamldecode(
    file("${path.module}/config/pipes.yml")
  )
}
Key concept
YAML
 ↓
yamldecode()
 ↓
Terraform objects

This is the core of our metadata-driven Terraform design.

Step 14 — Flatten metadata into Terraform-friendly structures

Example for tables:

tables = flatten([
  for source_name, source_config in local.tables_config : [
    for table_config in source_config.tables : {
      key          = "${source_name}.${table_config.name}"
      source       = source_name
      database     = source_config.database
      table_name   = table_config.name
      landing_type = table_config.landing_type
    }
  ]
])

Then:

tables_map = {
  for table in local.tables :
  table.key => table
}

So:

dim_customer.DIM_CUSTOMER
dim_product.DIM_PRODUCT
fact_internet_sales.FACT_INTERNET_SALES

become Terraform keys.

Why for_each?

Because Terraform can dynamically create infrastructure from metadata.

Step 15 — Create JSON file formats dynamically

file-formats.tf:

resource "snowflake_file_format_json" "json" {
  for_each = local.file_formats_map

  database = var.snowflake_database
  schema   = snowflake_schema.landing.name

  name = upper(
    "FF_${each.value.source}_${each.value.format_name}"
  )
}

Terraform now dynamically creates:

FF_FACT_INTERNET_SALES_JSON_FF
FF_DIM_CUSTOMER_JSON_FF
FF_DIM_PRODUCT_JSON_FF
Important lesson

We initially used an older generic resource, then corrected it to:

snowflake_file_format_json

because the Snowflake provider has moved toward specialized resources.

Step 16 — Create GCS external stages dynamically

stages.tf:

resource "snowflake_stage_external_gcs" "gcs" {
  for_each = local.stages_map

  database = var.snowflake_database
  schema   = snowflake_schema.landing.name

  name = upper(each.value.stage_name)

  url = each.value.gcs_path

  storage_integration = "ADVWORKS_GCS_INT"
}

This creates:

Step 17 — Create VARIANT landing tables dynamically

tables.tf:

resource "snowflake_table" "landing_variant" {
  for_each = {
    for table in local.tables_map :
    table.key => table
    if table.landing_type == "variant"
  }

  database = var.snowflake_database
  schema   = snowflake_schema.landing.name
  name     = each.value.table_name

  column {
    name = "RAW_DATA"
    type = "VARIANT"
  }

  column {
    name = "SOURCE_FILE"
    type = "VARCHAR"
  }

  column {
    name = "LOAD_TIMESTAMP"
    type = "TIMESTAMP_NTZ"

    default {
      expression = "CURRENT_TIMESTAMP()"
    }
  }
}

This creates:

DIM_CUSTOMER
DIM_PRODUCT

with:

RAW_DATA       VARIANT
SOURCE_FILE    VARCHAR
LOAD_TIMESTAMP TIMESTAMP_NTZ
Important

FactInternetSales is marked:

landing_type: typed

so this resource intentionally does not create the Fact table.

We are avoiding accidentally replacing the existing working typed Fact table.

Step 18 — Create Snowpipes dynamically

pipes.tf:

resource "snowflake_pipe" "landing" {
  for_each = local.pipes_map

  database = var.snowflake_database
  schema   = snowflake_schema.landing.name

  name = upper(each.value.pipe_name)

  auto_ingest = true

  integration = "ADVWORKS_GCS_PUBSUB_INT"

  copy_statement = <<-SQL
    COPY INTO ${var.snowflake_database}.${snowflake_schema.landing.name}.${each.value.table}
    FROM @${var.snowflake_database}.${snowflake_schema.landing.name}.${upper(each.value.stage)}
    FILE_FORMAT = (
      FORMAT_NAME = '${var.snowflake_database}.${snowflake_schema.landing.name}.${upper("FF_${each.value.source}_${each.value.file_format}")}'
    )
    ON_ERROR = 'CONTINUE'
  SQL
}

Terraform now understands the complete Snowpipe definition.

Example generated pipe:

COPY INTO ADVWORKS_TEST.LANDING.DIM_CUSTOMER
FROM @ADVWORKS_TEST.LANDING.STAGE_DIM_CUSTOMER
FILE_FORMAT = (
  FORMAT_NAME =
  'ADVWORKS_TEST.LANDING.FF_DIM_CUSTOMER_JSON_FF'
)
ON_ERROR = 'CONTINUE'

The most important interview takeaway

If an interviewer asks:

"Why did you use YAML with Terraform instead of hardcoding every Snowflake object?"

Your answer:

"We separated infrastructure logic from infrastructure metadata. Terraform contains the reusable resource definitions, while YAML defines source-specific metadata such as tables, stages, file formats and pipes. Terraform uses yamldecode, for expressions and for_each to dynamically provision the resources. This makes onboarding a new source mostly a configuration change rather than requiring new Terraform resource blocks, which is more scalable and consistent with an enterprise metadata-driven ingestion framework."

That's the core lesson of everything we've done so far.
