# Terraform SOP — Metadata-Driven Snowflake Infrastructure

## Project Goal

Convert manually created Snowflake landing infrastructure into **Terraform-managed, metadata-driven infrastructure**, following the enterprise pattern.

The goal is not merely to create Snowflake objects with Terraform. The goal is to understand how a production ingestion platform can be **configured, provisioned, validated, and deployed automatically**.

# 2. Metadata-Driven Design

Terraform Metadata-Driven Infrastructure
                    │
                    ▼
              YAML Metadata
                    │
                    ▼
              Terraform locals
                    │
                    ▼
                 for_each
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
       GCP                   Snowflake
        │                       │
       GCS                  Stages
        │                  File Formats
     Pub/Sub               Tables
        │                  Notification
        │                  Integration
        │                  Snowpipes
        │                       │
        └───────────┬───────────┘
                    ▼
              EVENT-DRIVEN
               INGESTION
                    │
                    ▼
                 LANDING
                    │
                    ▼
                 1,000 rows
                    ✅

The central design is:

```text
YAML
 │
 │ yamldecode()
 ▼
Terraform locals
 │
 │ flatten()
 │
 │ for_each
 ▼
Terraform resources
 │
 ▼
GCP + Snowflake infrastructure
```

Instead of creating this:

```text
resource "snowflake_table" "dim_customer" {}
resource "snowflake_table" "dim_product" {}
resource "snowflake_table" "fact_sales" {}
resource "snowflake_pipe" "dim_customer" {}
resource "snowflake_pipe" "dim_product" {}
...
```

we describe infrastructure through metadata:

```text
tables.yml
stages.yml
file-formats.yml
pipes.yml
```

This allows a new source to be onboarded primarily through configuration rather than writing a completely new Terraform resource block.

# Step 2 — Configure Terraform Backend

`versions.tf`:

```hcl
terraform {
  required_version = ">= 1.5.0"

  backend "gcs" {
    bucket = "electric-tesla-507710-k2-tfstate"
    prefix = "terraform/state/dev"
  }

  required_providers {
    snowflake = {
      source  = "snowflakedb/snowflake"
      version = "~> 2.0"
    }

    google = {
      source  = "hashicorp/google"
      version = "~> 8.0"
    }
  }
}
```

### Architecture

```text
Terraform
    │
    ▼
GCS Remote State
    │
    ├── Terraform state
    ├── Resource IDs
    ├── Dependency information
    └── Current infrastructure state
```

### Why remote state?

Without remote state:

```text
Developer laptop
     ↓
terraform.tfstate
```

With remote state:

```text
Developer / CI/CD
        ↓
     GCS State
        ↓
Shared Terraform state
```

This is essential for:

* CI/CD
* multiple developers
* state locking
* consistent infrastructure management

### Important

Never commit:

```text
terraform.tfstate
terraform.tfstate.backup
private keys
passphrases
service-account JSON
```

# Step 4 — Configure Snowflake Provider

`main.tf`:

```hcl
provider "snowflake" {
  organization_name = var.snowflake_organization_name
  account_name      = var.snowflake_account_name
  user              = var.snowflake_user

  authenticator          = "SNOWFLAKE_JWT"
  private_key            = file(var.snowflake_private_key_path)
  private_key_passphrase = var.snowflake_private_key_passphrase

  role = var.snowflake_role

  preview_features_enabled = [
    "snowflake_notification_integration_resource",
    "snowflake_table_resource",
    "snowflake_pipe_resource"
  ]
}
```

### Authentication

We use:

```text
Snowflake
    ↑
JWT / Key Pair Authentication
    ↑
Private key
```

The private key is stored locally:

```text
C:\Users\Admin\.snowflake\snowflake_tf_key.p8
```

The passphrase is supplied through an environment variable.

Example:

```powershell
$env:SNOWFLAKE_PRIVATE_KEY_PASSPHRASE="..."
```

### Security rule

Never put this in Git:

```text
snowflake_tf_key.p8
SNOWFLAKE_PRIVATE_KEY_PASSPHRASE
password
service-account.json
```

Current correct configuration:

`config/tables.yml`

```yaml
fact_internet_sales:
  database: ADVWORKS
  tables:
    - name: FACT_INTERNET_SALES
      landing_type: variant

dim_customer:
  database: ADVWORKS
  tables:
    - name: DIM_CUSTOMER
      landing_type: variant

dim_product:
  database: ADVWORKS
  tables:
    - name: DIM_PRODUCT
      landing_type: variant
```

### Important correction

Initially we used:

```yaml
landing_type: typed
```

for FactInternetSales.

That was changed.

The final practice architecture uses:

```text
VARIANT landing
```

for all three sources.

Why?

Because the enterprise-style landing layer should initially preserve the raw source payload.

```text
Raw JSON
   ↓
VARIANT
   ↓
PREPARE
   ↓
NORMALIZE
   ↓
SCHEMATIZE
```

This gives us schema flexibility and preserves the raw ingestion payload.

# Step 16 — Flatten Metadata

Continue `locals.tf`:

```hcl
locals {
  tables = flatten([
    for source_name, source_config in local.tables_config : [
      for table_config in source_config.tables : {
        key          = "${source_name}.${table_config.name}"
        source       = source_name
        database     = source_config.database
        table_name   = table_config.name
        landing_type = table_config.landing_type
      }
    ]
  ])

  stages = flatten([
    for source_name, source_config in local.stages_config : [
      for stage_name, stage_config in source_config : {
        key        = "${source_name}.${stage_name}"
        source     = source_name
        stage_name = stage_name
        gcs_path   = stage_config.gcs_path
      }
    ]
  ])

  file_formats = flatten([
    for source_name, source_config in local.file_formats_config : [
      for format_name, format_config in source_config : {
        key         = "${source_name}.${format_name}"
        source      = source_name
        format_name = format_name
        type        = format_config.type
      }
    ]
  ])

  pipes = flatten([
    for source_name, source_config in local.pipes_config : [
      for pipe_name, pipe_config in source_config : {
        key          = "${source_name}.${pipe_name}"
        source       = source_name
        pipe_name    = pipe_name
        stage        = pipe_config.stage
        stage_subdir = pipe_config.stage_subdir
        file_format  = pipe_config.file_format
        table        = pipe_config.table
      }
    ]
  ])

  tables_map = {
    for table in local.tables :
    table.key => table
  }

  stages_map = {
    for stage in local.stages :
    stage.key => stage
  }

  file_formats_map = {
    for format in local.file_formats :
    format.key => format
  }

  pipes_map = {
    for pipe in local.pipes :
    pipe.key => pipe
  }
}
```

Example generated Terraform keys:

```text
fact_internet_sales.FACT_INTERNET_SALES
dim_customer.DIM_CUSTOMER
dim_product.DIM_PRODUCT
```

and:

```text
fact_internet_sales.pipe_fact_internet_sales
dim_customer.pipe_dim_customer
dim_product.pipe_dim_product
```

# Step 17 — Understand for_each

Terraform can now do:

```hcl
for_each = local.tables_map
```

instead of creating individual resources.

Conceptually:

```text
tables.yml
    │
    ├── Customer
    ├── Product
    └── Fact
         │
         ▼
     tables_map
         │
         ▼
       for_each
      /   |   \
     /    |    \
Customer Product Fact
```

### Why this matters

Adding a new source becomes:

```text
Add YAML metadata
       ↓
terraform plan
       ↓
Terraform creates required objects
```

rather than:

```text
Create new .tf resource
Create dependencies
Create names
Create pipe
Create stage
Create file format
Repeat
```

# Step 20 — Create VARIANT Landing Tables Dynamically

`tables.tf`

```hcl
resource "snowflake_table" "landing_variant" {
  for_each = {
    for table in local.tables_map :
    table.key => table
    if table.landing_type == "variant"
  }

  database = var.snowflake_database
  schema   = snowflake_schema.landing.name
  name     = each.value.table_name

  column {
    name = "RAW_DATA"
    type = "VARIANT"
  }

  column {
    name = "SOURCE_FILE"
    type = "VARCHAR"
  }

  column {
    name = "LOAD_TIMESTAMP"
    type = "TIMESTAMP_NTZ"

    default {
      expression = "CURRENT_TIMESTAMP()"
    }
  }
}
```

Creates:

```text
DIM_CUSTOMER
DIM_PRODUCT
FACT_INTERNET_SALES
```

with:

```text
RAW_DATA        VARIANT
SOURCE_FILE     VARCHAR
LOAD_TIMESTAMP  TIMESTAMP_NTZ
```

### Why VARIANT?

Raw source JSON can be stored without forcing the landing layer to know every business column.

Example:

```json
{
  "CustomerKey": 11000,
  "FirstName": "John",
  "LastName": "Smith",
  "YearlyIncome": 50000
}
```

becomes:

```text
RAW_DATA
   ↓
VARIANT
```

Transformation happens later.

# Step 24 — Configure GCS Object Notifications

```hcl
resource "google_storage_notification" "snowpipe" {
  bucket         = var.gcp_bucket_name
  payload_format = "JSON_API_V1"

  topic = google_pubsub_topic.snowpipe.id

  event_types = [
    "OBJECT_FINALIZE"
  ]

  depends_on = [
    google_pubsub_topic_iam_member.gcs_publisher
  ]
}
```

### Why OBJECT_FINALIZE?

The event is generated when a new object is successfully created.

Example:

```text

Pub/Sub message
```

Final `pipes.tf`:

```hcl
resource "snowflake_pipe" "landing" {
  for_each = local.pipes_map

  database = var.snowflake_database
  schema   = snowflake_schema.landing.name

  name = upper(each.value.pipe_name)

  auto_ingest = true

  integration = snowflake_notification_integration.gcp.name

  copy_statement = <<-SQL
    COPY INTO ${var.snowflake_database}.${snowflake_schema.landing.name}.${each.value.table}
    (
      RAW_DATA,
      SOURCE_FILE
    )
    FROM (
      SELECT
        $1,
        METADATA$FILENAME
      FROM @${var.snowflake_database}.${snowflake_schema.landing.name}.${upper(each.value.stage)}
    )
    FILE_FORMAT = (
      FORMAT_NAME = '${var.snowflake_database}.${snowflake_schema.landing.name}.${upper("FF_${each.value.source}_${each.value.file_format}")}'
    )
    ON_ERROR = 'CONTINUE'
  SQL

  depends_on = [
    snowflake_table.landing_variant
  ]
}
```

### Why the SELECT?

This was an important implementation issue.

A JSON file format cannot directly map a JSON object into multiple normal table columns when the target landing table is:

```text
RAW_DATA VARIANT
SOURCE_FILE VARCHAR
```

Therefore:

```sql
SELECT
    $1,
    METADATA$FILENAME
```

maps:

```text
JSON payload
    ↓
RAW_DATA VARIANT

GCS filename
    ↓
SOURCE_FILE VARCHAR
```

### Result

```text
GCS JSON
   │
   ▼
Snowpipe
   │
   ├── $1
   │    ↓
   │  RAW_DATA
   │
   └── METADATA$FILENAME
        ↓
      SOURCE_FILE
```

`LOAD_TIMESTAMP` is automatically populated by:

```sql
CURRENT_TIMESTAMP()
```

```text
                    Database

                    Schema

 File Format         Stage            Table

                       ▲
```

The Snowpipe contains:


Terraform dependencies can be:

```text
Implicit
```


or:

```text
Explicit
```

using:

```hcl
depends_on = [...]
```

Use explicit dependencies when Terraform cannot correctly infer the runtime dependency.

# Step 55 — Interview Questions You Should Be Able to Answer

## Q1. Why Terraform?

**Answer:**

> "I use Terraform to manage Snowflake and GCP infrastructure as code. Instead of manually creating stages, file formats, landing tables, notification integrations and Snowpipes, I define them declaratively so infrastructure is version-controlled, repeatable and deployable through CI/CD."

---

## Q2. Why use YAML?

**Answer:**

> "YAML separates source-specific infrastructure metadata from reusable Terraform resource logic. Terraform uses `yamldecode`, locals and `for_each` to dynamically provision resources. This makes onboarding a new source primarily a metadata change instead of requiring new Terraform resource blocks."

---

## Q3. Why use `for_each`?

**Answer:**

> "`for_each` allows Terraform to create multiple resources from a metadata map. For example, the same Snowpipe resource definition can create FactInternetSales, DimCustomer and DimProduct pipes based on YAML configuration."

---

## Q4. Why use VARIANT in the landing layer?

**Answer:**

> "The landing layer is intended to preserve the raw source payload. VARIANT allows us to ingest JSON without tightly coupling the raw layer to a predefined relational schema. Business transformations and type conversions happen downstream in dbt."

---

## Q5. What is the difference between Terraform and dbt?

**Answer:**

> "Terraform manages infrastructure, such as Snowflake databases, schemas, stages, tables, integrations and Snowpipes. dbt manages data transformation, modelling, testing and documentation from LANDING through the analytical layers."

---

## Q6. Explain Snowpipe auto-ingestion.

**Answer:**

> "A new object is finalized in GCS, which generates an OBJECT_FINALIZE event. The event is published to Pub/Sub. Snowflake's notification integration listens to the Pub/Sub subscription, and the Snowpipe uses the notification to identify the new file and execute its COPY statement into the landing table."

---

## Q7. Why do we need Pub/Sub?

**Answer:**

> "Pub/Sub provides the event notification mechanism between GCS and Snowflake. Instead of continuously polling the bucket for new files, Snowflake can react to object-finalize events."

---

## Q8. Why `depends_on`?

**Answer:**

> "Terraform normally infers dependencies from resource references, but some runtime dependencies are not fully represented in the Terraform expression graph. I used explicit `depends_on` for the Snowpipe-to-table dependency because the pipe creation could otherwise occur before the landing table existed."

---

## Q9. What happens if Terraform state is wrong?

**Answer:**

> "Terraform compares configuration against its state and the real infrastructure. If the wrong workspace or state is used, Terraform may interpret resources from another environment as needing replacement. Therefore environment-specific state/workspaces and careful plan review are critical."

---

## Q10. Why remote state?

**Answer:**

> "Remote state provides a shared source of truth for Terraform infrastructure and is essential for collaborative development and CI/CD. It also prevents each developer or pipeline from maintaining an isolated local state."

# Final Interview Summary

If asked:

### "Explain your Terraform implementation."

Use this:

> "I built a metadata-driven Terraform framework for a Snowflake ingestion pipeline. YAML files define source-specific metadata for landing tables, GCS stages, JSON file formats and Snowpipes. Terraform reads that metadata using `yamldecode`, transforms it through locals and `flatten`, and uses `for_each` to dynamically create the infrastructure. GCP resources such as Pub/Sub topics, subscriptions, GCS notifications and IAM are also managed through Terraform. Snowflake uses a GCS storage integration and Pub/Sub notification integration for event-driven Snowpipe ingestion. The landing layer uses VARIANT to preserve raw JSON, while dbt owns downstream transformations from LANDING through PREPARE, NORMALIZE, SCHEMATIZE and MARKETPLACE. The infrastructure is stored in remote GCS state and is designed to be promoted through Azure DevOps CI/CD across DEV, TEST, PREPROD and PROD."

That is the **core story of this entire Terraform phase**.
