# 15. Why PostgreSQL?

Airflow needs a metadata database.

It stores information such as:

```text
DAG runs
Task instances
Task states
Connections
Variables
Schedules
Metadata
```

In this practice setup:

```text
PostgreSQL 13
```

is used.

---

# 16. Why RabbitMQ?

CeleryExecutor needs a message broker.

The scheduler can send work through the broker:

```text
Scheduler
    |
    v
RabbitMQ
    |
    v
Worker
```

RabbitMQ therefore distributes task execution messages.

---

# 17. Why CeleryExecutor?

`CeleryExecutor` allows task execution to be distributed across workers.

Conceptually:

```text
Scheduler
    |
    +--> task 1
    +--> task 2
    +--> task 3
             |
             v
          RabbitMQ
             |
       +-----+-----+
       |           |
    Worker 1    Worker 2
```

This is closer to a distributed production Airflow architecture than a single-process executor.

## Added

```text

```




# 32. Why Detect Changes Instead of Copying Everything?

Full-copy approach:

```text
Repository
    ↓
copy everything
    ↓
PROD
```

Problem:

```text
Developer A changes A
Developer B changes B

A deployment can accidentally promote B.
```

Controlled deployment:

```text
Commit A
   ↓
git diff
   ↓
A only
   ↓
PROD
```

This is safer for multi-developer environments.

# 36. Why `trigger` and `pr` Are Different

```yaml
trigger:
  branches:
    include:
      - main
```

means:

```text
push/commit to main
→ pipeline
```

Whereas:

```yaml
pr:
  branches:
    include:
      - "*"
```

means:

```text
PR validation
→ pipeline
```

This allows:

```text
feature branch
     ↓
PR validation
     ↓
merge main
     ↓
main deployment pipeline
```

# 41. Interview Questions — Architecture

### Q1. Why should PROD not directly copy the TEST bucket?

**Answer:**

Because TEST can contain changes from multiple developers or branches. Copying the entire TEST bucket can unintentionally promote unrelated work. A commit-based changed-file deployment limits the deployment to the intended A/M/D/R changes.

---

### Q2. How do you handle a renamed DAG?

**Answer:**

Git detects the rename using:

```bash
git diff --name-status -M
```

The pipeline treats the rename as:

```text
delete old object
+
copy new object
```

---

### Q3. Why use `R*` rather than `R100`?

**Answer:**

Git can report different rename similarity percentages, such as:

```text
R100
R095
R090
```

Therefore the pipeline checks for a status beginning with `R`.

---

### Q4. How do you make deletion idempotent?

**Answer:**

Check whether the GCS object exists before deleting it:

```bash
gcloud storage ls "gs://bucket/path/file"
```

If it exists, delete it. If it does not exist, log that it is already absent and continue.

---

### Q5. What happens if unit tests fail?

**Answer:**

The deployment stages depend on successful upstream execution, so TEST/PROD deployment does not proceed.

---

### Q6. Why does PROD depend on TEST?

**Answer:**

To establish a promotion sequence:

```text
TEST
 ↓
PROD
```

The PROD deployment should not become an independent parallel deployment.

---

### Q7. What does `condition` do?

**Answer:**

It determines whether a stage/job is eligible to execute based on runtime variables and previous results.

---

### Q8. What does `dependsOn` do?

**Answer:**

It defines the dependency relationship between stages/jobs.

---

### Q9. What does an Azure Environment approval do?

**Answer:**

It provides a deployment authorization/check for the target environment. For PROD, the pipeline can pause until the required approval/check succeeds.

---

### Q10. Why isn't approval the same as `condition`?

**Answer:**

A condition determines whether the deployment is eligible. Approval is an authorization/check after eligibility has been established.

---

### Q20. What is the difference between CI and CD?

**Answer:**

CI focuses on validating and integrating code changes. CD focuses on delivering validated code through deployment environments.

---

### Q21. Why deploy only changed files?

**Answer:**

To avoid promoting unrelated developer changes and to reduce the deployment scope.

---

### Q22. What is the current limitation of the controlled deployment design?

**Answer:**

It identifies the changes associated with a deployment, but it does not yet provide full protection against an older deployment executing after a newer deployment and overwriting shared files.

---

# 45. Interview Questions — Production Scenarios

### Q23. Developer A changes file A and Developer B changes file B. Can A's deployment copy B?

**Answer:**

With the controlled deployment design, A's deployment processes only the changes in A's commit, so B's unrelated file is not copied merely because it exists in TEST.

---

### Q24. Developer B deploys first and Developer A deploys an older commit later. Is the system fully protected?

**Answer:**

No. The current changed-file mechanism prevents unrelated file promotion, but an older deployment can still modify a file that was subsequently changed by a newer deployment. Deployment ordering/version protection is a separate concern.

---

### Q25. How would you explain this distinction?

**Answer:**

There are two independent problems:

```text
Change scope
=
Which files belong to this deployment?

Deployment concurrency
=
Is this deployment newer/older than the state already in PROD?
```

The current implementation solves the first problem but not the second.

# 49. The Core Interview Story

If asked:

> "Tell me about the Airflow CI/CD architecture you implemented."

A concise technical explanation is:

```text
I built a practice Airflow deployment architecture based on the
Enterprise-style setup using Dockerized Airflow with CeleryExecutor,
PostgreSQL and RabbitMQ.

The Airflow DAGs and plugins are stored in Git and validated using
pytest inside the same custom Airflow Docker image stored in Google
Artifact Registry.

After code is merged to main, Azure DevOps runs the unit tests and
then deploys only the files changed by that commit to a TEST GCS
bucket.

The deployment detects Added, Modified, Deleted and Renamed files
using git diff --name-status -M. Renames are implemented as delete
old object plus copy new object, and deletes are made idempotent by
checking object existence first.

The PROD stage depends on TEST, requires the main branch condition,
and is associated with a PROD Azure Environment where an approval
can be configured before the actual production deployment.

I also tested multi-developer scenarios to verify that a deployment
does not simply copy the complete TEST environment into PROD.
One remaining advanced concern is protection against out-of-order
deployments, where an older deployment could modify a file after a
newer deployment.
```
