1. What Airflow actually does

Your architecture should be understood as:

                    APACHE AIRFLOW
                         │
              ┌──────────┼──────────┐
              │          │          │
              ▼          ▼          ▼
           Python       GCS      Snowpipe
          Extraction   Validation  Monitoring
              │                     │
              ▼                     ▼
             GCS                Snowflake
                                    │
                                    ▼
                                   dbt
                                    │
                                    ▼
                              Data Quality

Airflow's job is:

Orchestrate, schedule, monitor, retry and coordinate tasks.

It should not become the system responsible for doing everything itself.

For example:

Python → extraction
GCS → storage
Pub/Sub → event notification
Snowpipe → ingestion
Snowflake → storage/SQL processing
dbt → transformation/modeling
Terraform → infrastructure
Airflow → orchestration

That distinction is one of the most important Airflow interview concepts.

5. Step 61 — Production-Safe File Naming

Your current DimProduct process can overwrite:

DimProduct_batch_001.jsonl

That isn't desirable for repeated Airflow runs.

Instead:

dim_product/
    run_date=2026-09-16/
        DimProduct_20260916_182403_001.jsonl

or:

dim_product/
    DimProduct_batch_20260916_182403_001.jsonl

The second approach is easier for your current project.

Why?

Imagine:

Run 1 → DimProduct_batch_001.jsonl
Run 2 → DimProduct_batch_001.jsonl
Run 3 → DimProduct_batch_001.jsonl

You lose historical objects.

Instead:

Run 1 → DimProduct_batch_20260916_182403_001.jsonl
Run 2 → DimProduct_batch_20260916_190501_001.jsonl
Run 3 → DimProduct_batch_20260917_090002_001.jsonl

Now every run has an identifiable object.

Interview question

Q: Why should data pipelines avoid overwriting raw files?

Answer:

Raw data should generally be immutable because it provides lineage, replayability and auditability. If a pipeline fails downstream, we should be able to reprocess the original input without depending on the source system again.

6. Step 62 — Create a Proper Airflow DAG

Your DAG should evolve from:

extract_data >> validate_extraction

toward:

extract_data >> validate_gcs >> validate_landing >> dbt_run >> dbt_test

Example:

from airflow.sdk import dag, task
from datetime import datetime


@dag(
    dag_id="advworks_pipeline",
    start_date=datetime(2026, 9, 16),
    schedule=None,
    catchup=False,
    max_active_runs=1,
    tags=["adventureworks", "data-engineering"],
)
def advworks_pipeline():

    @task
    def extract_data():
        import sys

        sys.path.insert(
            0,
            "/opt/airflow/python-ingestion"
        )

        from Stage_8_GCS_extract_all_tables_using_airflow import run_ingestion

        result = run_ingestion()

        if result["status"] != "success":
            raise RuntimeError("Extraction failed.")

        return result


    @task
    def validate_extraction(result):

        if result["status"] != "success":
            raise RuntimeError(
                "Extraction validation failed."
            )

        for table in result["tables"]:
            print(
                f"{table['table']} | "
                f"{table['mode']} | "
                f"{table['rows_extracted']}"
            )

        return "validation_success"


    extraction = extract_data()

    validation = validate_extraction(
        extraction
    )

    extraction >> validation


advworks_pipeline()
7. Step 63 — Understand XCom Properly

Your current:

return result

from:

extract_data()

is using XCom.

Conceptually:

extract_data
     │
     │ result
     ▼
XCom
     │
     ▼

Example:

@task
def extract():
    return {
        "status": "success",
        "rows": 606
    }


@task
def validate(result):

    if result["status"] != "success":
        raise RuntimeError("Failed")

    print(result["rows"])

Airflow handles the task dependency and XCom automatically.

Important interview point

Don't say:

"XCom is used to transfer data between tasks."

Better:

"XCom is intended for small pieces of metadata or control information between tasks, such as row counts, file paths, status flags or IDs. I would not use XCom to move large datasets because that creates metadata-database pressure and is not an appropriate data-transfer mechanism."

Very important.

Interview

Q: How do you handle transient failures in Airflow?

Answer:

"I configure task-level retries with an appropriate retry delay and use exponential backoff where necessary. I distinguish transient failures from permanent failures because retrying a bad SQL query or invalid schema indefinitely doesn't solve the underlying problem."

Interview question

Q: Why would you use catchup=False?

Answer:

"If a DAG is deployed today with a historical start date, Airflow can create runs for missed scheduled intervals. For pipelines where historical backfill is not automatically desired, I use catchup=False and trigger historical processing explicitly when needed."

15. Catchup vs Backfill

This distinction is frequently asked.

Catchup

Airflow scheduler behavior for missed scheduled intervals.

Backfill

Explicitly requesting historical runs.

Example:

DAG starts:
2026-01-01

Today:
2026-09-16

With catchup enabled, Airflow may create historical runs.

Backfill is something you intentionally request.

17. Poke vs Reschedule

Important Airflow concept.

Poke

Sensor keeps running while waiting.

Reschedule

Sensor releases its worker/execution slot and comes back later.

For long waits:

Reschedule-style behavior can be more resource efficient.

Modern Airflow also has deferrable operators, which move waiting work to the triggerer.

32. How do you make Airflow pipelines idempotent?

Answer:

"I use deterministic business keys, unique batch or run identifiers, immutable raw objects where possible, watermarks or CDC checkpoints, and MERGE/upsert logic downstream. Retries should produce the same logical result rather than duplicate business records."

33. How would you prevent duplicate data when Airflow retries?

Answer:

"I don't rely on Airflow retries alone. I design the task and downstream load to be idempotent. For example, the extraction generates a unique run or batch identifier, the raw object is uniquely identified, and Snowflake uses the appropriate key and MERGE/deduplication strategy."

34. What happens if Airflow succeeds but Snowpipe hasn't loaded the data?

Answer:

"I would separate extraction success from downstream ingestion success. Airflow should validate that the expected batch has appeared in Snowflake before starting dbt. Because Snowpipe is asynchronous, I would use a bounded wait/check mechanism with a timeout rather than assuming that successful GCS upload means successful Snowflake ingestion."

35. How would you handle a slow source database?

Answer:

"First I'd determine whether the problem is query performance, source contention, network throughput or extraction design. Then I'd use incremental extraction, appropriate indexing/query predicates, batching and controlled Airflow concurrency. I would avoid simply increasing parallelism because that could make the source problem worse."

36. How would you handle 10 million records?

Answer:

"I wouldn't use XCom or the Airflow metadata database to transfer the records. I'd extract in batches to object storage, use the cloud-native ingestion mechanism to load the warehouse, and pass only metadata such as file paths, row counts and batch IDs through Airflow."

37. What happens if Airflow scheduler goes down?

Answer:

"The scheduler is responsible for scheduling rather than being the business data store. In a properly deployed Airflow environment, the metadata database preserves DAG and task state, and scheduler availability is restored through restart or high-availability configuration depending on the deployment architecture."

🏆 Your Airflow Interview Story

For your own project, eventually answer like this:

"I designed Airflow as the orchestration layer for an end-to-end AdventureWorks pipeline. SQL Server acts as the source, Python performs extraction and incremental processing, GCS is the raw landing layer, Pub/Sub and Snowpipe handle event-driven ingestion into Snowflake, and dbt performs transformation and data quality testing. Airflow coordinates these stages, manages dependencies, retries, validation, auditing and scheduling. I use XCom only for small metadata such as row counts, file paths and run information, while actual data remains in GCS or Snowflake."

Then add:

"For incremental processing I use watermark/CDC logic, and downstream Snowflake MERGE/SCD logic provides idempotency and history management. In production I would replace local ADC authentication with workload identity and use a secrets backend rather than storing credentials in DAG code."

That one answer connects Airflow + Python + GCS + Pub/Sub + Snowpipe + Snowflake + dbt + CDC + security + production architecture.
