Interview answer

If asked:

How do you prevent duplicate ingestion with Snowpipe?

A good answer is:

"Snowpipe maintains ingestion metadata at the file level. When a previously ingested file generates another notification, Snowpipe doesn't normally load it again. 
However, I don't rely on that alone for end-to-end idempotency. I also design audit keys, source-file tracking, load timestamps, 
business keys and downstream merge logic depending on the pipeline."

That's much stronger than simply saying "Snowpipe prevents duplicates."

Don't say:

"Snowpipe guarantees idempotency."

That's too broad.

Say:

"Snowpipe maintains file ingestion metadata and normally prevents the same file from being automatically loaded again. 
However, REFRESH can discover files that aren't recorded as loaded by that pipe, and application-level idempotency still needs to be designed for renamed files, 
regenerated files, CDC, retries, and downstream transformations."

Next - > Pipeline Monitoring & Audit

What we're going to learn

A production pipeline needs to answer:

What happened to my file?

For example:

DimCustomer_batch_019.jsonl
        ↓
Was it uploaded?
        ↓
Did GCS receive it?
        ↓
Did Pub/Sub receive the event?
        ↓
Did Snowpipe process it?
        ↓
How many rows were loaded?
        ↓
Did dbt process those rows?
        ↓
Did data-quality tests pass?
        ↓
Did it reach the final model?

This is called pipeline observability / lineage / auditability.

1. Infrastructure-level monitoring

We already have several checks.

GCS
gcloud storage ls "gs://advworks-dev-ingestion/dim_customer/"

This answers:

Did the file arrive in GCS?

2. Pub/Sub

We can inspect the subscription:

gcloud pubsub subscriptions describe dev-gcs-events-sub --project=electric-tesla-507710-k2

This answers things such as:

subscription exists
topic connection
acknowledgement configuration
retry/dead-letter configuration if configured
3. Snowpipe

We already learned this:

SELECT SYSTEM$PIPE_STATUS(
    'ADVWORKS_DEV.LANDING.PIPE_DIM_CUSTOMER'
);

This answers:

Is the pipe running?
Is there a backlog?
What was the last ingested file?
When was it ingested?
Are messages waiting?

This is one of our primary operational checks.

4. LANDING audit

Our landing tables already have:

RAW_DATA
SOURCE_FILE
LOAD_TIMESTAMP

That is actually very useful.

For example:

SELECT
    SOURCE_FILE,
    COUNT(*) AS ROW_COUNT,
    MIN(LOAD_TIMESTAMP) AS FIRST_LOAD_TIME,
    MAX(LOAD_TIMESTAMP) AS LAST_LOAD_TIME
FROM ADVWORKS_DEV.LANDING.DIM_CUSTOMER
GROUP BY SOURCE_FILE
ORDER BY LAST_LOAD_TIME DESC;

This gives us a basic file-level audit.

For our current data, we can see something like:

SOURCE_FILE                                  ROW_COUNT
------------------------------------------------------
dim_customer/DEV_TEST_DimCustomer_001.jsonl     5000
dim_customer/DimCustomer_batch_001.jsonl        1000
...
But production systems need something better

Instead of relying only on the actual business tables, we normally create an audit/control table.

For example:

PIPELINE_AUDIT
------------------------------------------------------
RUN_ID
PIPELINE_NAME
SOURCE_SYSTEM
SOURCE_FILE
START_TIME
END_TIME
STATUS
ROWS_READ
ROWS_WRITTEN
ERROR_COUNT
ERROR_MESSAGE

Then a pipeline execution could produce:

RUN_ID     SOURCE_FILE             STATUS    ROWS
--------------------------------------------------
10001      batch_001.jsonl         SUCCESS   1000
10002      batch_002.jsonl         SUCCESS   1000
10003      batch_003.jsonl         FAILED       0
10004      batch_003.jsonl         SUCCESS   1000

Now an engineer can answer:

"What happened to batch 003?"

without manually inspecting every system.

If asked "How do you monitor a data pipeline?", don't answer only:

"I check whether the Airflow DAG is green."

Instead:

"I monitor both orchestration and data-level outcomes. I track execution status, source and target objects, start/end times, rows read/written, 
error counts and error details in an audit layer. The orchestration tool provides task-level visibility, while the audit framework provides data-level traceability."

That's the distinction we're building toward.
