# PART 1 — MY PROJECT

## 1.1 60-SECOND INTRODUCTION

I built an end-to-end cloud data engineering platform using AdventureWorks as the source system.

The source data originates in SQL Server. I use Python to extract and batch the data, serialize it into files and land it in Google Cloud Storage.

The ingestion layer moves the data into Snowflake, where I maintain separate logical layers for LANDING, PREPARE, NORMALIZE, SCHEMATIZE and MARKETPLACE.

dbt manages SQL transformations, dependencies, testing and dimensional modeling.

Airflow provides orchestration and controlled DAG deployment.

Terraform manages infrastructure as code, including Snowflake and cloud resources.

Azure DevOps provides CI/CD automation, while GitHub is used for source control.

For authentication between Azure DevOps and Google Cloud, I implemented Workload Identity Federation rather than storing long-lived service-account JSON keys.

The pipeline also includes GCS, Pub/Sub, Snowpipe, IAM, environment isolation, automated validation, approvals, data-quality checks and deployment controls.

The important part is that I validated the pipeline end to end rather than only creating individual components.

## Q2. OLTP vs OLAP?

OLTP is optimized for transactional workloads.

Examples:

* order creation
* payment
* customer update

Characteristics:

* frequent writes
* short transactions
* normalized schemas
* high concurrency

OLAP is optimized for analytics.

Characteristics:

* large scans
* aggregations
* historical analysis
* dimensional models
* analytical queries

---

## Q3. Why shouldn't I run heavy analytical queries directly against OLTP?

Because analytical workloads can:

* consume CPU
* consume memory
* cause locking/contention
* increase query latency
* affect application performance

A common architecture is:

```text
OLTP
 ↓
Extraction
 ↓
Data Platform
 ↓
Warehouse
 ↓
Analytics
```

# PART 3 — EXTRACTION

# 5. FULL LOAD

## Q4. What is a full load?

A full load extracts the complete source dataset.

```text
Source
 ↓
Extract all rows
 ↓
Landing
 ↓
Target
```

Advantages:

* simple
* easy to understand
* easy initial load

Disadvantages:

* expensive at scale
* slower
* unnecessary repeated processing

---

# 6. INCREMENTAL LOAD

## Q5. What is incremental extraction?

Extract only records that changed since the previous successful run.

Example:

```sql
SELECT *
FROM Customer
WHERE LastModifiedDate > :watermark;
```

Architecture:

```text
Previous watermark
       ↓
Source query
       ↓
Changed records
       ↓
Landing
       ↓
Target
       ↓
New watermark
```

---

# 7. WATERMARKS

## Q6. What is a watermark?

A watermark represents the latest successfully processed source position.

Examples:

```text
last_modified_timestamp
identity value
sequence number
LSN
SCN
event offset
```

Example:

```text
Previous watermark:
2026-09-25 10:00:00

Extract:
WHERE modified_at > '2026-09-25 10:00:00'
```

After successful processing:

```text
New watermark:
2026-09-26 10:00:00
```

Important:

The watermark should normally advance **only after successful processing**.

---

# 8. CDC

## Q7. What is CDC?

CDC means Change Data Capture.

It identifies source changes such as:

```text
INSERT
UPDATE
DELETE
```

Instead of repeatedly extracting the entire table, the pipeline consumes changes.

---

## Q8. CDC vs incremental timestamp extraction?

Timestamp approach:

```text
WHERE updated_at > watermark
```

CDC:

```text
Database change
 ↓
CDC mechanism
 ↓
Change event
 ↓
Pipeline
```

Timestamp extraction may miss changes when:

* timestamps are unreliable
* deletes aren't represented
* records are updated without changing the timestamp

CDC can capture inserts, updates and deletes depending on the implementation.

---

## Q9. What CDC technologies might you encounter?

Examples:

* SQL Server CDC
* SQL Server Change Tracking
* transaction logs
* Oracle redo logs
* Debezium
* Kafka Connect
* database-native replication
* cloud CDC services

---

# 9. CDC INTERVIEW SCENARIO

## Q10. A record is inserted and updated five times before your pipeline runs. Do you need all five versions?

Depends on the business requirement.

If the warehouse only needs the latest state:

```text
A
 ↓
B
 ↓
C
 ↓
D
 ↓
E
```

may be collapsed to:

```text
E
```

If audit/history is required, all changes may need to be retained.

Therefore CDC design depends on:

* business requirement
* audit requirements
* warehouse model
* event ordering
* retention

# PART 4 — EXTRACTION ENGINEERING

# 10. BATCHING

## Q11. Why batch extraction?

Instead of:

```python
rows = cursor.fetchall()
```

for millions of records, process chunks.

```python
while True:
    rows = cursor.fetchmany(batch_size)

    if not rows:
        break

    process(rows)
```

Benefits:

* lower memory usage
* easier retry
* predictable file sizes
* scalable processing

---

# 11. PAGINATION

For APIs:

```text
GET /customers?page=1
GET /customers?page=2
GET /customers?page=3
```

or cursor-based:

```text
response
 ↓
next_cursor
 ↓
next request
```

Cursor pagination is usually safer for changing datasets because page numbers can shift when records are inserted.

# 12. SERIALIZATION

## Q12. What is serialization?

Serialization converts in-memory objects into a transferable/storable representation.

Examples:

```text
Python object
 ↓
JSON
```

or:

```text
DataFrame
 ↓
Parquet
```

---

# 13. JSON vs JSONL vs CSV vs PARQUET

| Format  | Strength                  |
| ------- | ------------------------- |
| CSV     | Simple/interoperable      |
| JSON    | Nested/semi-structured    |
| JSONL   | Streaming/record-oriented |
| Parquet | Columnar/analytical       |
| Avro    | Schema + row-oriented     |
| ORC     | Columnar analytical       |

For analytical workloads, columnar formats such as Parquet are often more storage/query efficient.

---

# 14. DATA TYPES DURING SERIALIZATION

A common problem:

```python
json.dumps({
    "amount": Decimal("100.50"),
    "created": datetime.now()
})
```

may fail because Decimal/datetime aren't directly JSON serializable.

A quick fallback:

```python
json.dumps(record, default=str)
```

But production pipelines should define explicit type conversion because blindly converting everything to strings can cause downstream type-quality problems.

Object storage provides:

* separation of storage and compute

# PART 9 — SCD

# 32. SCD TYPE 0

Never change the original value.

---

# 33. SCD TYPE 1

Overwrite.

```text
Toronto
   ↓
Montreal
```

Only Montreal remains.

---

# 34. SCD TYPE 2

Preserve history.

```text
Customer 100

Toronto
2024-01-01 → 2025-01-10
is_current = false

Montreal
2025-01-11 → NULL
is_current = true
```

Typical columns:

```text
effective_from
effective_to
is_current
```

---

# 35. SCD TYPE 2 IMPLEMENTATION

Conceptually:

```sql
MERGE INTO dim_customer target
USING staging_customer source
ON target.customer_id = source.customer_id
AND target.is_current = TRUE

WHEN MATCHED
AND target.city <> source.city
THEN UPDATE SET
    target.is_current = FALSE,
    target.effective_to = CURRENT_TIMESTAMP;
```

Then insert the new version.

In practice, implementation must also handle:

* duplicate source records
* same-day changes
* late-arriving data
* deletes
* null comparison
* transaction boundaries

# 41. DBT MATERIALIZATIONS

Important materializations:

```text
view
table
incremental
ephemeral
snapshot
```

### View

Stores SQL definition.

### Table

Physically materializes results.

### Incremental

Processes only new/changed data according to model logic.

### Ephemeral

Used as an intermediate CTE-like model and isn't directly materialized.

### Snapshot

Tracks historical changes to records.

---

# 42. DBT INCREMENTAL MODEL

Example:

```sql
{{ config(
    materialized='incremental',
    unique_key='CUSTOMER_KEY'
) }}

SELECT *
FROM {{ ref('customer_prepare') }}

{% if is_incremental() %}

WHERE LOAD_TIMESTAMP >
      (SELECT MAX(LOAD_TIMESTAMP)
       FROM {{ this }})

{% endif %}
```

Important interview discussion:

`is_incremental()` does not magically make a model incremental.

The engineer must define correct incremental filtering and merge behavior.

# PART 12 — IDEMPOTENCY

# 56. WHAT IS IDEMPOTENCY?

An operation is idempotent if repeating it produces the same correct result.

Example:

```text
Process file A
Process file A again
```

should not create duplicate business records.

---

# 57. HOW DO YOU MAKE A PIPELINE IDEMPOTENT?

Techniques:

* MERGE
* unique business keys
* processed-file tracking
* deterministic identifiers
* checkpointing
* transactional writes
* overwrite partition
* deduplication

---

# 58. IDEMPOTENCY SCENARIO

Suppose:

```text
Batch 100
```

loads 10,000 rows.

The task fails after Snowflake receives them.

The task retries.

Without idempotency:

```text
20,000 rows
```

With idempotency:

```text
10,000 correct rows
```

Therefore:

```text

 ↓
fails

```

Task logic should tolerate repeated execution.

---

# 74. ACKNOWLEDGEMENT

A consumer acknowledges successful processing.

If a message isn't acknowledged, depending on configuration it can be redelivered.

Therefore consumers should be idempotent.

# 75. DEAD LETTER QUEUE

This prevents poison messages from repeatedly blocking the normal pipeline.

# PART 26 — SQL INTERVIEW MASTER SET

# 118. WHERE VS HAVING

```sql
SELECT customer_id, COUNT(*)
FROM sales
WHERE order_date >= '2026-01-01'
GROUP BY customer_id
```

`WHERE` filters rows before aggregation.

`HAVING` filters groups after aggregation.

# PART 27 — PYTHON INTERVIEW MASTER SET

# 127. GENERATOR

```python
def read_batches(cursor, batch_size):
    while True:
        rows = cursor.fetchmany(batch_size)

        if not rows:
            break

        yield rows
```

Generators avoid loading the entire dataset into memory.

---

# 128. RETRY

```python
import time

for attempt in range(3):
    try:
        process()
        break
    except TimeoutError:
        if attempt == 2:
            raise

        time.sleep(2 ** attempt)
```

Production implementations should distinguish retryable and non-retryable exceptions.

# 130. EXCEPTION HANDLING

Never silently swallow important failures.

# PART 54 — GOLDEN RULE

Never answer only with a textbook definition.

Instead:

```text
Definition
    ↓
Why
    ↓
How
    ↓
My implementation
    ↓
Code/example
    ↓
Failure scenario
    ↓
Production consideration
    ↓
Trade-off
```

For example:

Instead of:

> "Terraform is Infrastructure as Code."

Say:

> "Terraform is a declarative Infrastructure as Code tool. In my project I used it to manage infrastructure and Snowflake resources, kept the state remotely in GCS, separated DEV and TEST state, validated changes through Azure DevOps and used plan/apply stages with deployment controls. The important production consideration is protecting state because it represents Terraform's understanding of the real infrastructure."

That answer demonstrates:

```text
Concept
+
Implementation
+
Architecture
+
Security
+
CI/CD
+
Production thinking
```
