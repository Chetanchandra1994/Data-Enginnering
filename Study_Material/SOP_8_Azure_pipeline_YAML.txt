#############################################  Step 2.1 "PyTest" Python Testing Framework -  ############################################# 

What exactly is pytest?

pytest is a Python testing framework.

Think of it as a test runner:

Your Python code
      │
      ▼
Your test cases
      │
      ▼
    pytest
      │
      ├── discovers tests
      ├── executes tests
      ├── evaluates assertions
      └── reports PASS / FAIL

Pytest does not inherently know:

"This Airflow operator should return X."

You write that expectation yourself.

For example:

def test_addition():
    result = 2 + 3

    assert result == 5

Pytest runs it.

Because:

result = 5
expected = 5

the assertion:

assert result == 5

is true.

Therefore:

PASSED

If the code were:

result = 2 + 4

assert result == 5

then:

6 == 5

is false.

Therefore:

FAILED

That's the fundamental mechanism.

So what is your pipeline actually testing?

Your Azure command is:

pytest Tests/ -v

The important part is:

Tests/

Pytest recursively looks inside that directory for test files.

Your project has:

airflow-practice/
│
├── Tests/
│   └── operators/
│       └── test_extraction.py
│
├── plugins/
│
├── DAGS/
│
└── ...

So pytest discovers:

Tests/operators/test_extraction.py

and executes the test functions/classes inside it.

Your current suite contains 5 tests around the extraction operator.

What does a test actually look like?

The basic pattern is:

def test_something():
    # Arrange
    ...

    # Act
    ...

    # Assert
    assert ...

This is an extremely important Data Engineering/testing concept.

1. Arrange

Prepare the situation.

For example:

operator = ExtractionOperator(...)
2. Act

Run the functionality:

result = operator.some_method(...)
3. Assert

Check whether the result is what you expect:

assert result == expected

So:

Arrange
   ↓
Act
   ↓
Assert
   ↓
PASS / FAIL
How does pytest determine PASS or FAIL?

The key word is:

assert

For example:

assert result == expected

Python evaluates:

result == expected

If it is:

True

the test passes.

If it is:

False

Python raises an AssertionError.

Pytest catches that and reports:

FAILED
There are many types of checks

For example:

Equality
assert actual == expected
Not equal
assert actual != expected
True/False
assert result is True
None
assert result is not None
Contains
assert "CustomerKey" in result
Length
assert len(records) == 1000
Exception

You can test that invalid input correctly raises an exception:

with pytest.raises(ValueError):
    function_with_invalid_input()

So a test isn't necessarily checking one particular type of value.

It can check whatever behavior you explicitly define.

In your Airflow project

One more important distinction

There are several levels of testing you will eventually encounter in your Data Engineering project:

1. Unit Test
      ↓
Test one small piece of code

2. Integration Test
      ↓
Test interaction between components

3. Data Quality Test
      ↓
Test the actual data

4. End-to-End Test
      ↓
Test the complete pipeline

For example:

      ↓
Does its logic work?

      ↓
Can these components communicate correctly?

      ↓

    ↓

    ↓

    ↓

    ↓
Snowpipe
    ↓

That final one tests the whole data path.

So remember this simple definition

Pytest is a Python testing framework that discovers and executes test cases. The test cases contain assertions that define what behavior is expected. If the assertions succeed, pytest reports PASS; if an assertion fails or an unexpected error occurs, pytest reports FAIL and returns a failure exit code.

And in your current Azure pipeline, pytest is currently being used for unit testing the Airflow/Python code, specifically your existing extraction tests—not for validating the entire SQL Server → GCS → Snowflake pipeline.

Step 1 — What is this test file testing?

The file tests one specific piece of your Airflow code:

Its purpose appears to be determining whether the extraction should use:

fullload

or

stream

as the target file prefix.

So the business logic being tested is essentially:

Does this extraction have a previous checkpoint/XCom?
        |
        +-- YES → stream
        |
        +-- NO → fullload

Unless source.file_prefix explicitly overrides it

The tests also check that target connectors cannot override the prefix chosen by the source/ExtractionOperator logic.

Step 2 — First understand the test structure

Every test follows this pattern:

SETUP → ACT → ASSERT

For example:

# Setup
operator.source.xcom_key = 'last_record_ts'

# Act
determined = operator._determine_prefix(ti)

# Assert
assert determined == 'stream'

Meaning:

Setup

Create a particular situation.

Act

Run the code being tested.

Assert

Check whether the result is what we expect.

That assert is what ultimately determines PASS or FAIL.

Step 3 — What does the fixture do?

At the beginning:

This is a pytest fixture.

Whenever a test contains:

pytest automatically executes the operator fixture first and gives the test this object.

So instead of repeating:

mock_source = MagicMock()
mock_targets = [...]
operator = ExtractionOperator(...)

in all five tests, you define it once.

The fixture creates:
ExtractionOperator

        |

              +-- MagicMock()
              +-- MagicMock()

So these tests are not connecting to SQL Server, Oracle, GCS, Snowflake, etc.

They are testing the Python logic in isolation.

Step 4 — What is MagicMock()?

This is important.

Normally your operator might have a real source connector:

SQL Server connector
Oracle connector
Progress connector

But testing against a real database would make this a much heavier test.

Instead:

mock_source = MagicMock()

creates a fake object.

You can tell the fake object:

mock_source.xcom_key = 'last_record_ts'

or:

mock_source.file_prefix = 'stream'

without needing a real connector.

Similarly:

ti = MagicMock()

creates a fake Airflow Task Instance.

Then you can control what happens when the operator calls:

ti.xcom_pull(...)

For example:

ti.xcom_pull.return_value = '2026-05-14 10:00:00'

means:

Whenever the code calls ti.xcom_pull(), pretend that Airflow returned this timestamp.

Your current pytest setup is checking five expected behaviors of ExtractionOperator._determine_prefix():

1. XCom exists
       → stream

2. XCom doesn't exist
       → fullload

3. Source explicitly says stream
       → stream

So when Azure runs:
